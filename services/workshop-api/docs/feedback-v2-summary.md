# Feedback V2 工作总结

## 一页结论

Feedback V2 将“提交一条反馈”升级为“可持续沟通、可流转待办、可回写状态”的反馈闭环：用户提交后可以补充消息和附件，开发者可回复，反馈流转为待办后会随待办状态更新。

升级不替换 V1。V1 接口、现有 SDK、iOS 与待办 Web 保持可用；V2 通过独立路由和项目灰度开关逐步启用。

V2 同时提供两种接入方式：有宿主服务端时使用短期会话 token；没有服务端或追求快速接入时，可沿用客户端配置 API Key 的模式，并明确接受其风险。

## 为什么做

| 原始需求 | V2 的回应 |
| --- | --- |
| 反馈提交后无法继续沟通 | 建立用户、开发者、系统三类消息时间线 |
| 需要补充图片、文件等证据 | 附件归属到每条消息，支持上传、读取和预览 |
| 流转为待办后，反馈状态不跟随变化 | 建立反馈与待办关联，待办状态自动回写反馈 |
| 现有接入量大，不能强制升级 | V1 保持兼容，V2 独立发布和按项目灰度 |
| API Key 放在客户端简单但有风险 | 安全模式与直连模式并存，由接入方显式选择 |

## 设计方向

1. **闭环而非孤立表单**：反馈、会话消息、消息附件、待办关联是四个独立但关联的数据对象；一条反馈可完整保留上下文。
2. **增量演进而非推倒重来**：复用原有 `feedbacks` 表，只增加字段、表和索引；V1 的 JSON 数据与接口契约不变。
3. **隔离发布而非全量切换**：V2 使用 `/workshop/v2`；控制台按项目启用，未开启项目继续走 V1。
4. **安全与易用并存**：完整方案让 API Key 留在接入方服务端；直连方案保留移动端、WebView 常见的简单配置体验。
5. **附件按权限读取**：上传使用受限策略，读取按反馈或待办关联校验后签发短期权限，不将私有对象直接公开。

## 已完成能力

- V2 反馈创建时原子写入首条用户消息，历史 V1 反馈已可回填为会话首条消息。
- 用户与开发者可在同一反馈下双向发送消息，每条消息可包含图片、文件和 HTTPS 链接。
- 客户端重试使用 `client_message_id` 幂等，避免网络波动造成重复消息。
- 反馈可流转为待办；流转时已存在的会话附件会以待办评论形式带入，并保留原消息文字上下文。
- 待办状态变化会同步回反馈，并写入系统消息；控制台和 SDK 查询时可展示最新状态。
- 控制台支持 V2 灰度、会话查看、开发者回复以及私有附件的临时预览。
- SDK 同时支持安全会话模式和客户端直连 API Key 模式；两种模式都覆盖反馈、消息与附件能力。

## 工作路径

1. **梳理现状**：确认 V1 的反馈创建、查询、OSS、控制台和待办流转链路，识别“无消息、状态不回写、附件孤立”三类缺口。
2. **建立数据与迁移基础**：新增会话、附件、待办关联表和可回滚迁移；迁移保持追加式，避免破坏现存数据。
3. **完成后端闭环**：实现 V2 路由、消息接口、首次消息、幂等、附件策略、流转待办和状态回写。
4. **解决接入安全与兼容**：实现短期 scoped token 链路，同时保留显式风险接受的 API Key 直连链路。
5. **完成控制台与 SDK 接入**：控制台按项目灰度，SDK 支持两种模式、消息会话、附件上传和状态刷新。
6. **端到端验证与修正**：验证状态同步、私有附件预览和待办评论；修正了“用户补充附件未带入待办评论”的问题。

## 发布策略

| 层级 | 策略 |
| --- | --- |
| 数据库 | 仅新增字段、表、索引；先备份，迁移显式执行且可回滚 |
| 网关 | 增加 V2 `feedback` 认证级别，不改变既有 JWT/API Key 路径 |
| Workshop 服务 | 同时注册 V1/V2；V1 业务路由保持原样 |
| 控制台与 SDK | 先部署静态资源，再仅为测试项目打开 V2；其他项目仍使用 V1 |
| 回滚 | 关闭项目 V2 开关即可停止新增 V2 流量；V1 不依赖 V2 新表 |

## 下一步

1. 以测试项目完成安全模式与直连模式的完整回归：提交、消息、附件、流转、状态回写、刷新与重试。
2. 按项目逐步启用 V2，不进行全量切换；观察错误率、附件读取与 WebView 兼容性。
3. 完成接入文档和自动化测试后，沉淀为 V2 接入 Skill，覆盖 Web、iOS、Android、宿主服务端以及无服务端直连场景。
4. 后续业务迭代聚焦通知、未读、已读回执和更丰富的待办协作，不改变当前兼容与鉴权边界。

<details>
<summary>实现细节：数据模型与兼容策略</summary>

- `feedbacks` 保留原有记录；增加结构化状态与最近消息时间。
- `feedback_messages` 保存 customer、developer、system 消息；`feedback_message_attachments` 保存消息级附件。
- `feedback_task_links` 保存反馈与待办的关联，待办更新时据此回写反馈状态。
- 历史数据回填首条消息，旧 SDK 仍可从原字段和 `data` 读取状态。
- V2 路由在 `/workshop/v2`，消息和流转能力不加入 V1，避免扩大 V1 改动面。
</details>

<details>
<summary>实现细节：两种鉴权模式</summary>

**安全会话模式**：接入方服务端持有 Workshop API Key，按已登录用户调用 `POST /workshop/v2/apikey/feedback-sessions`，向客户端只返回短期、绑定项目和用户范围的 token。适合有服务端和真实用户身份的业务。

**客户端直连模式**：SDK 配置 API Key、`projectId` 和稳定 `customUserId` 后，直接调用 `/workshop/v2/apikey/*`。适合移动端、WebView 和没有宿主服务端的快速接入；API Key 被打入客户端，应使用项目专用 Key、支持轮换，并避免可猜测的用户 ID。
</details>

<details>
<summary>实现细节：已知边界</summary>

- 待办只会带入“流转当时已存在”的消息附件；流转后的新消息不会自动写入待办评论，仍保留在反馈会话中。
- V2 控制台采用项目灰度，不能直接把全局 `VITE_API_URL` 从 V1 改为 V2。
- 数据库回滚必须先回滚应用并确认不再读取新结构；对已经产生真实 V2 消息的环境，优先停灰度并保留数据，而不是直接删除新表。
</details>
