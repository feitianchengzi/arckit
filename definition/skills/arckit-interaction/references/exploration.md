# 探索、比较与采纳

用于探索或采纳时读取。正式预期持续维护；探索是候选空间，不是正式规格的替代品。

## 存放与关联

- 交互探索：`arckit/interaction/_explorations/<topic>/`。
- 每个主题包含 `exploration.md` 和按需建立的 `options/<name>/`；候选可以复用稳定资源，但独立模拟状态不能污染正式原型或其他候选。
- `_explorations/INDEX.md` 登记主题、入口和状态；正式 INDEX 只保留探索索引入口，不把候选列成已完成页面。
- 视觉候选归 `arckit/visual/_explorations/`。联合探索只选一个主题说明作为比较/采纳记录，另一个域引用它；交互候选引用视觉候选，不复制规范。两侧 skill 均描述自己的输入、产物和维护职责，无隐藏调用。
- 基础设施目录豁免页面目录规则；正式业务页面仍按真实页面或稳定路由归属。

## 最小探索记录

`exploration.md` 包含：问题与范围、保持不变的要求、基线文件与版本（Git revision 加相关未提交快照说明，或内容摘要）、各候选入口及设计意图、比较结论、待决定问题、采纳记录。
比较使用相同任务和样本内容，说明变化维度。可以固定视觉比较交互，也可以固定交互比较视觉，不必制造全部组合。
候选状态用候选 / 已采纳 / 部分采纳 / 未采纳 / 已过时；“已过时”说明基线变化及影响，不自动删除候选。
没有正式基线时写明“尚无”，记录用户输入和约束；允许在探索内形成假设策略，不反向写成正式依据。

## 采纳与组合

1. 检查用户选择或已有明确授权依据；已选择的无需再次审批。未选择时先完成可比较材料，再列具体待决定项。
2. 核对候选基线与当前正式事实；正式事实已变时标记受影响部分并核对，不盲目覆盖。
3. 记录整案或分项采纳：来源候选、采纳部分、不采用部分、依据和正式目标路径。
4. 更新正式策略、原型、说明；视觉部分先有正式视觉依据，再由交互原型应用。另一域的修改超出当前授权/能力边界时回传具体交接，不能宣称整合完成。
5. 检查组合后的导航、术语、状态流、组件层级与视觉一致性，沿完整操作路径验证。
6. 正式稿必须完整，不要求实施者继续拼装候选。选择记录留在探索区，正式正文只描述有效预期。

普通维护无需创建探索目录。候选不因生产已经实现而自动获选；正式预期也不因上线而停止维护。


## 结果与执行边界

按 [设计产物结果契约](../../_arckit_shared/design-result-contract.md) 返回结果。仅要求制作和比较时，候选已完成但尚未采纳不构成本轮人工阻塞；要求采纳时才按当前必要决定报告 needs_human。跨域交接不强制另开执行者、轮次或 gap，同一 Agent 可在当前授权与目标内使用两种能力同步同一结论。
