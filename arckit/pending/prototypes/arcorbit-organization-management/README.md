# ArcOrbit 组织管理中心 — 待确认交互方案

## 状态

- State: candidate
- Case: `CASE-20260818-002`
- Gap: `GAP-MANAGEMENT-DESIGN`
- 结论用途：供用户确认，不是正式 interaction、spec 或生产实现事实

## 问题判断

当前 ArcOrbit 把 `Products` 与 `Team` 放在 Today、Work、Automation、Feedback 同一层，并由当前 Workset 裁剪 Team 数据。这造成三个结构性问题：

1. “选择当前要同时展示哪些产品”和“管理组织下的项目”混在 Products 页面。
2. 组织、组织成员和项目成员只在当前 Workset 范围内出现，无法形成组织全貌。
3. 组织治理与具体产品推进并列，用户需要在推进任务时理解两套不同尺度的对象。

真实代码还存在会影响交互可信度的边界：

- Workshop 项目列表响应没有 `organization_id`，ArcOrbit 当前测试使用了服务端实际不会返回的模拟字段。
- 普通组织成员只能查询自己参与的项目；组织 owner/admin 可以通过独立接口查询组织全部项目。
- Workshop 已提供邀请码加入组织和项目的接口，ArcOrbit 目前只提供生成邀请，没有加入入口。
- Workshop 能创建项目邀请码，但没有查询项目邀请列表和撤销项目邀请的接口；生成结果目前只能作为一次性结果使用。
- 项目 `organization_id` 更新是临时迁移字段，服务端明确说明当前校验不完整，不适合作为普通项目编辑能力。
- Workshop 列表接口单页最多 200 条，ArcOrbit 当前没有持续分页，因此“完整”只在数据量较小时成立。
- 直接添加项目成员接口缺少服务端调用者权限校验，仍然不进入 ArcOrbit。

## 推荐的信息架构

```text
推进
  Today
  Work
  Automation
  Feedback

平台
  Organization

全局控制
  当前 Workset（同时展示哪些产品）
```

`Organization` 是治理入口，不受当前 Workset 裁剪。它内部按以下顺序展开：

```text
选择组织
  → 组织概览
  → 成员
  → 项目
```

“成员”和“项目”在数据上是组织下的两个关系集合，不伪装成严格父子实体。交互上先理解成员，再理解成员参与哪些项目；组织概览用成员 × 项目矩阵表达全貌。

## 主路径

### 1. 进入组织管理

- 左侧组织列表展示当前用户加入的全部组织，不使用 Workset 过滤。
- “个人项目”作为独立范围与组织并列，但不伪装为 Organization。
- 选择组织后保留在管理中心，不跳入某一个项目的 Work、Automation 或 Feedback。

### 2. 先看组织全貌

- 组织头部展示当前用户角色、成员数、可见项目数和当前 Workset 中的项目数。
- owner/admin 的“组织项目”使用 Workshop 管理接口读取全部项目。
- member 只显示当前用户参与的项目，并明确标注“可见范围”，不把局部数据说成组织全部项目。
- 成员 × 项目矩阵只读展示组织成员的项目参与、角色、职责和外部成员关系。

### 3. 管理组织成员

- 组织 owner/admin 可以编辑组织、生成组织邀请和移除非 owner 成员。
- 只有 owner 可以修改非 owner 成员的组织角色。
- 当前用户可以退出组织；owner 退出时明确说明服务端会进行所有权交接，最后一位成员不能退出。
- 增加“使用邀请码加入组织”入口，复用 Workshop 已有接口。
- 成员详情不提供“生成项目邀请”。项目邀请码不绑定目标成员，在成员上下文中生成会错误暗示系统已向该成员发起定向邀请。
- 成员的项目参与项只提供“查看项目”，需要新增项目关系时进入对应项目上下文。

### 4. 管理组织项目

- 在当前组织上下文创建项目；创建时固定归属当前组织。
- 项目详情分开显示 Workshop 项目事实、本地 repository 绑定、Workset 展示状态和 Automation participation，四者互不暗改。
- owner/admin 可以编辑名称和 Git URL，并在当前项目详情中发起“邀请成员加入此项目”。
- 只有 owner 可以删除项目和修改非 owner 成员的角色/职责。
- 增加“使用邀请码加入项目”入口，复用 Workshop 已有接口。
- 不提供普通“移动到其他组织”；等待服务端建立可靠的归属迁移契约。
- 不提供直接添加项目成员；邀请仍是安全加入路径。
- 项目邀请首先确认项目名称，再设置加入角色、有效期和最多使用次数。生成结果展示邀请码与加入链接，明确它不会自动发送给任何成员，由用户自行复制和分享。
- 接收者从全局“输入项目邀请码”入口加入，成功后重新同步项目成员。
- 在 Workshop 增加邀请列表和撤销接口之前，ArcOrbit 将该能力标注为“一次性生成与分享”，不虚构邀请管理、接收人或投递状态。

### 5. 配置 Workset

- Workset 控件继续位于全局顶栏，可从任何推进页面打开。
- 用户可同时勾选多个产品，也可以一个都不选。
- Workset 只改变 Today、Work 和普通 Feedback 的展示范围；不改变组织/项目成员关系、本地绑定、Automation participation 或活动执行。
- 在组织项目列表中可以看到“当前 Workset 中”，但勾选动作仍明确属于本地显示设置，不属于项目管理。

## 状态与恢复

- 组织为空：提供创建组织、输入邀请码加入组织、进入个人项目三个入口。
- 组织数据成功但成员或项目失败：保留已成功区段，显示区段级重试。
- member 可见范围受限：显示“我参与的项目”，不显示虚假的组织总数或空全貌。
- 超过一页：连续加载直到达到服务端 `total`；加载中展示已加载数量。
- 项目邀请生成成功：突出目标项目、邀请码、加入链接、角色、过期时间和最大使用次数；关闭前提示当前结果无法重新查询。
- 邀请加入失败：区分无效、过期、已用尽、已是成员和权限错误。
- 邀请无法查询或撤销：不展示虚假的邀请历史和撤销动作；将服务端能力缺口保留到后续实现 Gap。
- 删除或退出：确认页展示受影响对象；最终以服务端结果为准并重新同步。
- 组织被删除或权限变化：退出失效详情，回到组织列表并保留其他组织。

## 不改变的产品核心

- Product / Product Workspace 仍是研发业务主线；组织管理只属于统一平台底座。
- Workset 仍支持同时推进多个产品，不退化为产品切换器。
- ArcOrbit 的全局单活动执行、一个待办一个持续 thread、Case/Loop、人工介入与恢复不变化。
- Workshop 继续拥有组织、成员、项目和邀请数据；ArcOrbit 不建立第二套团队实体。
- 本地项目仍是 Agent 开发工作的锚点。

## 需要用户确认

1. 是否接受把 `Products` 和 `Team` 合并为一个平台级 `Organization` 管理入口。
2. 是否接受“组织概览 → 成员 → 项目”的任务顺序，并以只读成员 × 项目矩阵表达组织全貌。
3. 是否接受“个人项目”作为与组织并列的独立范围，而不是伪造一个个人组织。
4. 是否接受 Workset 继续留在全局顶栏、完全独立于组织治理。
5. 是否接受普通 member 只能看到“自己参与的项目”，owner/admin 才看到组织全部项目的真实权限差异。
6. 是否接受项目邀请只存在于项目上下文，并在当前服务能力下明确标注为“通用邀请码的一次性生成与分享”。

## 原型入口

打开 `index.html`。可操作内容：

- 切换组织与个人项目；
- 切换组织概览、成员、项目；
- 查看成员详情和项目详情；
- 编辑当前 Workset 的多产品选择；
- 从项目详情配置并生成通用邀请码，查看复制、分享、加入与同步说明；
- 查看普通成员权限下的受限项目视图。
