# State Driven Loop 与 Gap 选择：完整设计意图

## 文档定位与权威范围

本文集中记录用户关于 State Driven Loop 与 Gap 选择的设计动机、相关概念、完整机制和已确认边界，是后续机制优化、实现检查和案例分析的设计意图依据。

本文回答“希望 Agent 如何理解和推进事情，以及为什么”。它不描述某次任务的执行结果，不包含具体执行案例的评判，也不以当前 skill、状态字段、测试或 Runtime 的既有实现反向限定预期。

相关思考在本文中保持完整。其他产品规格、技术方案和 skill 是对这些意图的展开与实现；出现差异时，应显式识别差异并判断，而不是用实现现状默默改写设计意图。新的思考经确认后集中维护本文，具体案例的证据、评价和修复方案另行保存。

## 一、为什么需要 State Driven Loop 和 Gap 选择

不同事情需要不同的处理过程。一个故障可能先需要查清直接原因，一个功能可能首先缺交互定义，另一个任务可能主要难在技术可行性。不能仅因为用户希望最终得到可用软件，就把当前任务一概理解为代码实现。

让 Agent 一个 Gap 一个 Gap 地推进，是为了让当前最值得处理的问题得到充分思考，并让该问题产生的新事实真正影响后续选择。它保护的是问题判断、决定质量、事实顺序和结果可靠性。

Gap 选择不能只是一句抽象的“处理最重要的缺口”。Agent 必须理解自己在什么对象上、缺少哪方面的结论或证据、为什么优先处理它、如何证明它已解决，以及哪些责任仍未完成。

这套机制同时追求两件事：

- 重要、困难或会影响后续方向的问题得到独立处理，不被“整体完成任务”吞没。
- 紧密相关且适合共同处理的小问题可以合并，不把工作机械拆成大量细碎轮次。

完整目标的交付由这些有依据的局部推进累计形成。Gap 的数量、名称、账本写回次数和形式上的闭环，都不能替代真实目标的推进。

## 二、通用机制、场景定义与项目状态

### 通用 State Driven Loop

State Driven Loop 是行业、场景无关的通用机制。软件开发是当前采用的场景，不是通用机制的适用上限。

通用机制负责恢复目标和事实、发现缺口、检查前置、比较优先级、推进当前问题、形成证据、接受状态变化并重新判断。它不内置某个行业的固定阶段、工作类型、产物或 skill 顺序。

### 场景 State 定义

与场景强相关的是 State 本身的定义，包括：

- 需要理解的对象和关系。
- 必须考虑的不变量或责任。
- 事实类型及其依赖关系。
- 哪些结论需要什么证据。
- 什么条件下可以推进、验收和完成。
- 哪些决定由谁承担。

场景定义不仅是字段名称，还包含 Agent 判断这些状态时必须理解的语义。

切换场景时，可以明确替换场景定义及其状态校验、能力和证据适配，继续使用同一套通用 Loop。软件专属的不变量与事实顺序不应变成通用机制或 Runtime 内核中的固定业务分支。

### 具体项目 State

具体项目 State 保存这个项目当前的目标、已接受事实、维护对象、实现载体、实际状态、证据和未完成义务。

同属软件场景的项目可以有不同的产品、技术栈、维护对象和实现方式。项目个性化主要通过项目事实表达，不要求为每个项目重写通用 Loop。

## 三、目标、Case、Gap 与 Loop 的关系

| 概念 | 含义 | 与其他概念的边界 |
| --- | --- | --- |
| 用户目标 | 用户期望达成的结果及授权范围 | 给出最终方向，不自动决定处理流程或 Gap 数量 |
| Project State | 项目当前可恢复的事实与推进状态 | 为选择提供依据，不提供超出用户授权的新目标 |
| Case | 围绕一个授权事项保存目标、事实、相关义务和推进结果 | 承接整个事项，可以包含多个不同性质的 Gap |
| Gap | 当前目标中尚未成立、值得作为一个边界来处理的具体结果 | 说明缺少什么、为何要处理、成立需要什么证据 |
| Loop | 围绕选定 Gap 推进、形成证据、提交并重新判断的一轮 | 不等于一次工具调用；同一个 Gap 可以跨多轮完成 |

Case 的完整交付目标不能仅通过换一个标题就成为合理的 Gap。必须先理解目标内部的问题、前置、责任和取舍，再判断是否确实只剩一个可共同完成的结果。

反过来，小任务如果前置充分且确实只有一个有界结果，Case 与 Gap 范围可以一致，不为制造轮次而拆分。

一个 Gap 可以包含多个紧密相关的子结果，但它们必须共享目标、前提和验收边界。是否可以合并，不能只由“同一页面”“同一个需求”“同一批改动”或“同一授权”决定。

## 四、软件不变量的原始含义

任何软件开发任务，无论功能还是 Bug，都必须从以下六个方向逐项认真思考。方向表示需要承担的责任；不变量表达这些责任中应保持成立的条件。这是不可省略的分析下限，不是可以按直觉任选几项的清单。

| 方向 | 核心责任 |
| --- | --- |
| 产品需求 | 目标、能力、业务规则、范围和验收含义明确，有来源并可恢复 |
| 交互设计 | 用户动作、状态变化、反馈、异常和恢复行为明确、自洽 |
| 视觉规范 | 呈现、层级、组件与主题等有依据，与已接受的视觉要求一致 |
| 技术方案 | 技术决定、约束、关系和理由明确，关键可行性有相称证据 |
| 实现（原称代码实现） | 实际产物、行为和生效状态有证据；探索中的修改与观察如实表达，正式实现兑现已接受的相关预期 |
| 诊断根因 / Debug | 对异常现象的直接原因作出有证据的解释，区分观察、假设与因果结论 |

这里的“实现”承接最初所说的“代码实现”，但不把实现载体限定为代码，也不把该方向限定为正式交付。“兑现”描述正式实现与已接受预期的符合性；实现方向本身仍可以承担探索。

软件不变量是必要的下限，不是思考与责任的上限。六个方向都必须考虑，Agent 还应结合具体事情识别其他必要问题和责任，包括项目已有的其他长期约束。不能因为清单没有列出就忽略，也不能因六项均已考虑就认定任务已被完整理解。

强制的是完整思考，实际步骤、Gap 和处理方式由思考结果决定。是否需要逐一独立处理，不能预先要求，也不能预先排除：分析后六个方向都需要独立工作，就分别处理；适合共同处理的，依据事实关系和粒度边界合并；已有充分事实或确实无关的，分别说明依据。

选择之前，Agent 必须结合目标、现有事实、缺失和依赖逐项分析，明确每个方向已经具备什么、还缺什么、是否需要行动。不能先决定“我要改代码”，再根据准备修改的文件倒推哪些不变量相关；也不能只报“已考虑”，或到任务最后才把不变量当作检查清单补填。

逐项思考不能省略，思考后的处置可以不同：

- 已有事实充分：引用并说明依据，复用已有结论。
- 与当前目标确实无关：说明理由。
- 相关但缺失、冲突、过时或证据不足：保留为当前需要解决的具体义务。

“本轮不处理”不等于“不相关”。对未决责任的保留与对当前 Gap 的聚焦必须同时成立。

“不预设流程”不能成为省略分析或跳过必要工作的理由。需要补齐的责任必须实际补齐，执行组织形式在分析之后确定。

软件业务 Gap 应说明所承接的不变量责任，具体候选可以来自用户要求、现有预期、实现观察、反馈、依赖或其他真实证据。六个方向不构成封闭的任务分类；实际发现的其他必要责任应明确表达，不能为套入六类而扭曲或丢弃问题。一个 Gap 可以关联多个责任；责任交接或协议恢复等控制工作按自身契约处理，不伪装成软件业务问题。

## 五、不变量、预期事实、实现事实与因果结论

这些概念处于不同层次，不能互相代替。

| 概念 | 回答的问题 | 作用 |
| --- | --- | --- |
| 软件不变量 | 哪些责任或正确性条件必须得到保障？ | 强制逐项思考的最低要求，约束接受的状态，不限定全部问题与责任的上限 |
| 预期事实 | 软件或维护对象应该是什么？ | 提供需求、交互、视觉、技术约定与验收依据 |
| 实现事实 | 当前实际是什么、实际发生了什么？ | 记录实现载体、生效状态、运行行为及其证据 |
| 因果结论 | 相关现象为什么发生？ | 用证据解释直接原因，为后续处置提供依据 |
| 过程材料 | 当前有哪些假设、候选和未决判断？ | 保存探索过程，不自动成为正式预期或已证实结论 |

不变量本身不等于某份需求文档或某个文件必须被修改。它要求相应责任有成立依据；成立依据可能已经存在，也可能需要当前任务建立。

事实角色针对具体主张及材料用途判断，不把整份材料强制归入互斥的类别。同一份记录可以同时承载观察、原因假设、已证实的因果解释和待定方案，必须分别说明依据与接受状态。已证实的因果解释说明实际现象为何发生，不因此成为软件应该如何表现的要求。

一条事实被接受，只表示这条具体主张有依据，不代表其关联的不变量、其他主张或整个任务都已经完成。

实际存在的行为不自动成为正确预期。测试证明软件按某种方式运行，也不自动证明用户希望软件如此运行。诊断解释了原因，也不自动决定需求应当变化或修复已经完成。

## 六、实现事实取决于项目维护对象

实现事实与项目实际维护和交付的对象有关，不能只靠文件扩展名识别。

维护普通应用时，实现载体可以是程序、配置、资源和运行环境；维护 skill 时，直接决定 Agent 行为的技能正文、references、脚本和模板就是实现载体。定义该 skill 应具备哪些能力和边界的规格，则是预期事实。

Agent 必须理解：

- 当前项目维护的对象是什么。
- 哪些材料实际承载它的实现。
- 修改如何在目标环境中生效。
- 什么证据能说明实际行为满足预期。

源文件修改完成、生效完成和行为兑现是不同主张。修改了 Markdown 不一定是在维护预期；写了“应该”也不自动改变一份材料作为实现指令的角色。

这种识别应由 skill 的引导明确承接，不能只假定 Agent 会凭常识正确区分。

## 七、Debug 为什么属于软件不变量

Debug 的核心目标是找出相关异常的直接原因，而不是先把异常归类为需求、交互、技术或代码问题。

对于“按钮点击无效”这类问题，诊断先回答为什么点击没有产生预期响应。原因查清后，才依据该原因、已有预期和实际状态重新判断应该如何处理。

直接原因得到证实，不代表只要修改最直接的一处就必然解决完整问题，也不代表必须重做需求或技术方案。若现有预期有效，只是实现写错了，就进入实现修复。

Debug 可以被描述为一个过程，但其他方向也包含过程。它作为不变量所保障的是原因判断有依据、假设与结论可区分、未解释部分可恢复。每项任务都必须思考诊断责任；是否需要开展诊断、复用已有原因证据或说明不相关，由具体分析结果决定。

用户待解决的故障或影响后续处置的重要独立因果问题，直接原因未知时先诊断，取得结论后提交并重新选择。已有可靠原因证据时复用，不重复制造诊断轮次。

实现或实验中为证明当前既定结果所需的常规调查、排障和测试可以留在当前 Gap。若失败暴露独立重要原因未知，或动摇已有预期、关键前提或验收边界，则保留证据与义务并重新选择；不能仅凭“发生报错”或“正在实现”决定是否拆分。

## 八、横向责任与纵向业务对象

横向是不变量所表达的责任，纵向是当前实际处理的业务或问题对象，例如功能、模块、用户场景、故障或核心技术点。

选择 Gap 时，两者共同界定问题：在什么对象范围内，哪方面的责任尚未成立，缺少什么结果或证据。

这使 Agent 可以围绕一个模块或关键问题推进，而不是必须一次把整个项目某个方向的全部事实都定义完成。

横向完整考虑不等于纵向无限扩张：

- 局部结论只覆盖声明的范围和证据，不代表整个模块或项目已完成。
- 当前授权目标内的已知相关义务必须保留。
- 原任务之外的独立问题不因不变量检查自动变成必做事项。
- 共享前提的变化需要重审所有实际依赖它的局部，无关范围不自动失效。

局部推进与预期优先同时成立。它不允许 Agent 通过缩小描述，隐藏实际依赖的未决要求。

## 九、预期事实与实现事实的大方向顺序

正式实现依赖其范围及共享前提所需的预期事实。相关预期应当明确、有效、已接受，并足以指导实现与验收。

“预期优先”是选择资格约束，不只是优先级偏好。不能因为实现容易、影响面大或看起来很快，就绕过相关预期的缺失和冲突。

这一约束作用于真实依赖，不设置全项目或全 Case 的同步阶段：

- A 的相关预期充分，且不依赖 B 的未决问题时，A 实现和 B 的预期工作都可以成为候选。
- A、B 依赖的共享约定未定时，依赖它的正式实现尚不具备条件。
- 优先处理的 Gap 结束后，其余必要责任仍要补齐；各局部同样遵循相关预期先于正式实现。

判断预期是否充分，要看剩余未知的不同答案是否会改变当前外部行为、关键约束或验收标准，而不是只看文档是否存在、用户表述是否简短或 Agent 是否觉得容易实现。

用户明确、有效的要求可以直接构成预期依据；已有充分预期可以复用，不为格式齐全额外制造确认轮次。但用户目标明确，不自动证明产品、交互、视觉和技术层面的全部必要约定都已明确。

新建或改变的预期在负责该结论的 Gap 中维护到权威事实源，再选择依赖它的正式实现。不能先实现再把结果补写成预期，也不能把新的行为取舍仅称为“文档同步”而忽略其事实性质。

预期的接受遵循已有授权和决策权限，不等于每个 Gap 都要询问用户。Agent 可以在授权内作出有依据的决定；需要人承担的取舍、审美或授权仍保持相应责任。

## 十、探索与正式确立是另一条判断轴

事实方向和结论性质相互独立。产品、交互、视觉、技术、实现和诊断方向，都可能需要探索，也都可能形成正式结论。

探索回答未知、验证假设、比较候选并取得决定所需依据。正式确立则接受有依据的预期、因果结论，或者证明实际实现兑现了已接受预期。

不能把探索限定成“技术试验”，也不能把写代码一律判断为正式实现。原型、代码修改、资料调查或 skill 试跑都是方法，使用的方法不决定本轮接受什么结论。

探索先行必须由事实依赖触发：未知的不同答案会改变重要决定，而现有证据不足时，先处理能够回答这个未知的 Gap。机制必须引导 Agent 发现这项前置，而不只是列出一句“必要时可以探索”。

当前取证需要明确服务的目标或受阻决定、待回答问题、足够证据、条件与限制，以及哪些后续主张尚不能成立。

探索具备选择资格，要求的是当前取证所需的授权、范围、可执行条件和证据标准；不要求先把待探索的功能预期或待验证结论定稿。不能把探索要回答的未知本身，写成必须先满足才能开展探索的前置条件。

### 通过实现探索，再完善预期，再正式兑现

某些任务只有操作真实实现载体，才能确认可行性或发现正确方向。此时允许先通过实现探索，但三个结果必须分清：

1. 探索取得有边界的观察与证据，回答当前未知。
2. 根据新事实重新选择，正式完善相关产品、交互、视觉或技术预期。
3. 依据已接受预期，选择正式实现与验收。

这表达证据与决定的依赖，不是每项任务的固定三段流程。具体预期方向仍按问题的重要性、依赖和现有事实逐 Gap 选择。

探索期间，相关软件不变量分别承担责任：未决预期保持未决；关键可行性主张需要证据；真实修改及其对既有行为的影响如实记录；尚未兑现的正式目标继续保留。实验成功不能让所有相关不变量一并变为已满足。

实验观察可以是真实的实现事实，但不自动成为产品应该如此的依据，也不自动取得正式交付地位。实验引入的实际回归仍要承接，探索不豁免已有行为与授权约束。

可靠证明不可行也可以完成探索 Gap。仅仅试过、没有回答问题或证据仍不足时，保留原 Gap、已有证据和未决事项。

正式预期接受后，可以复用、调整并验收实验载体，不要求机械重写。

### 探索方法不自动产生额外 Gap

同一既定局部结果内的调查、比较和试验，可以是完成该结果的方法，不因使用探索方法就强制换 Gap。

如果当前结果只是取得某项依据，而其后还需要另行选择的重要决定或正式兑现，则在依据成立处提交并重新选择，不能顺带完成下游工作。

是否跨越边界取决于当前要验收的结果、前置和决定关系，不由“探索”标签、工具动作或已有文件决定。

## 十一、Gap 的发现、资格与优先级

选择从问题本身出发，而不是先选一个实现动作，再为它补充理由。

Agent 在当前事实下完成以下判断：

1. 恢复用户目标、授权范围及已有材料。
2. 识别纵向对象，强制逐项思考六个方向及当前其他不变量，同时发现清单之外的必要责任，区分已有依据、真实未决与确实无关的部分。
3. 形成当前事实支持的候选，保留已知义务及真实依赖。
4. 检查候选是否有资格推进，包括授权、责任、关键依据和正式实现所需预期。
5. 判断候选边界是否适合独立处理或合并。
6. 在合格候选中比较影响面、关键不确定性、风险及依赖，选择当前最值得解决的问题。

优先考虑影响面大、关键不确定性高、能够解除阻塞或减少重大返工的问题。这里的不确定性须与当前目标和后续决定有关，不能因某个边缘问题陌生而优先。

优先级是基于事实的比较，不是固定评分，也不是产品、交互、视觉、技术、实现、诊断的固定排序。不同事项可以自然选择不同的第一 Gap 和处理方法。

选择需要能够说明：

- 当前尚未成立的具体结果是什么。
- 缺少什么依据、决定或行动。
- 它成立后会改变什么。
- 为什么比其他当前候选更值得优先处理。
- 哪些证据足以验收。
- 哪些已知义务本轮不处理，以及如何保留。

已登记的候选不是问题全集。“只有一个已记录 Gap”不能替代对 Case 内部问题的分析；未登记但已被事实暴露的重要缺口仍要参与判断。

完整候选比较也不意味着声称穷尽所有未知问题。只保留真实已知和本轮实际发现的工作，不凭想象生成未来执行链。

## 十二、粒度：重要问题独立，相关小项合并

Gap 的粒度服务于判断质量和推进效率。

特别重要或特别困难的关键问题应独立处理，不能为了减少轮次并入一般工作。其判断依据包括答案影响后续方向或多个对象、需要独立取舍或授权，或者必须先得到它的答案才能决定其他工作。独立处理应说明究竟保护了哪项判断；难度指需要专门解决的未知或推理难点，不等于文件多、操作多或耗时长。

相关小项在共享目标、前提和验收边界，且不存在需要分开处理的重要取舍时，可以组成一个 Gap。产品、交互、视觉或技术中的紧密相关小结论可以共同完善；实现和证明该实现所需的验证也可以共同完成。

合并有明确边界：

- 不能只因同属一个任务、页面或模块而合并。
- 不能把独立重要问题藏进“整体实现与验证”。
- 不能把建立或修改预期与正式兑现实现合并到同一个 Gap。
- 不能用“都不难”或“没有重要取舍”把新预期当作已有预期。

是否新建或改变预期，决定是否跨越预期与实现的边界；决定的重要性与独立性，决定同类结果内部如何拆分或合并。这两种判断不能互相替代。

文件数量、测试数量、工作量和执行时长不直接决定 Gap 数量。一个大实现可以在前置已定的条件下围绕同一结果跨轮推进；一个工作量很小但会改变关键行为的决定，也可能值得独立处理。

同一 Gap 未完成时允许保留部分进展继续，不因换轮另起名称，也不能通过跨轮先定义预期、再在原 Gap 实现来绕过边界。

## 十三、执行、提交与重新选择

选定 Gap 后，Agent 动态使用必要的能力、skills 和工具。问题决定方法，专业 skill 的完整流程不自动扩大当前 Gap 的边界。

新的信息如果用于理解、证明或完成当前既定结果，可以继续使用。接口完成后进入联调、既定约束内调整实现手段等操作依赖，不自动成为新 Gap。

当前结果成立时提交；跨轮或交接时若证据不足，如实保留部分进展。当前结论解除了后续独立结果或重要决定的前置，需要据此选择下游工作时，先提交当前结论再重新判断，不能在原 Gap 顺带继续下游工作。新证据使已接受预期、关键前提、责任或验收边界需要重定时，保留证据与义务，提交后重新选择。

另一个候选存在或变为可执行，本身不表示当前仍然有效的 Gap 必须立即中断。新发现的独立问题保留为候选，不顺带解决；是否需要结束或重新界定当前工作，依据它是否改变当前结果、关键前提或决定边界判断。

提交后的重新选择基于可信的最新状态，不由上一轮预先决定下一 Gap，也不把写回结果直接当成新的候选依据。

如果已有 Gap 过宽或前提失效，可以明确重新界定，但必须保留已有证据、未完成责任和替代关系。取消不等于验收完成，也不撤回用户目标。

新知识出现、本轮结束和新建 Gap 是三件不同的事。动态推进既不意味着每有新信息就换 Gap，也不意味着把所有新问题不断塞回原 Gap。

## 十四、义务连续性、事实维护与完成

优先处理某个 Gap，只改变当前处理顺序，不免除其余相关软件责任。

所有当前已知、属于授权目标的必要缺口与真实依赖都应保留，包括开始时已经明确的义务。不预排流程不等于故意逐轮才披露已知问题。

结论形成或改变的当轮维护其权威事实载体，优先更新已有来源，不等任务最后统一补文档。已有依据充分时复用，不为不变量数量制造文档。

已满足的责任可以因新证据而重新变为未决或受威胁。局部完成不能代表整体成立，也不能用一次测试成功支持不同事实方向的全部主张。

完成以用户授权目标为边界：

- 完整开发任务最终补齐范围内所有必要责任，并证明预期得到兑现。
- 仅授权探索或定义时，完成相应结论、事实载体和证据，不扩展为未授权的整个产品实现。
- 尚未完成、等待人或外部条件、用户要求停止，与真实完成分别表达。
- 普通义务闭合后进行完成复审，检查正确性、问题是否解决、验证可信度、回归风险与最小性。

复审是最终保障，不能代替选择前的分析、过程中应完成的预期维护或重要问题的独立处理。账本接受和复审通过，也不能反过来证明此前的语义判断必然正确。

## 十五、语义判断与确定性保障的分工

Agent 负责理解目标、概念、事实和依赖，判断相关性、预期是否充分、探索是否足够、Gap 如何拆合，以及哪些工作最值得优先处理。

可信状态与 Ledger 负责版本、引用、依赖状态、声明结构、原子提交及可以确定性检查的冲突。Runtime 负责执行承接与恢复，不按关键词、路径、文件类型或固定业务路线替代 Agent 选择。

机制要让 Agent 显式表达当前结果、依据、结论性质、事实责任和剩余义务，并让这些判断可恢复、可检查。但字段填写正确不等于内容真实，形式门禁不能替代语义理解。

实现优化应围绕如何使这些判断稳定发生，而不是仅追加抽象规则、更多字段或更多轮次。具体字段和脚本属于技术实现，不构成本文设计意图的边界。

## 十六、对 skill 表达和可理解性的要求

一个未参与设计讨论的 Agent，应能依靠交付的 skill 及其明确引导读取的随包资料，理解上述概念、关系与行为边界，再结合真实业务项目的要求和事实执行。

这种理解不能依赖 Agent 已读过 Arckit 研发仓库、知道历史讨论，或由维护者在脑中补足省略的含义。

skill 需要把“为什么这样判断、在什么条件下选择什么结果、何时继续或重选”连接起来。示例帮助理解分界，但不能变成所有任务照抄的固定步骤。

稳定的维护对象、实现载体、生效和验证上下文可以保存并复用，减少重复表达；每轮仍须确认其适用性。当前范围、前置、验收、优先理由和未决义务由当前事实重新判断，不能因上下文复用而沿用过时选择。

新项目、新需求或新问题的可理解性检查，关注实际业务问题如何被分析、选择和推进；项目初始化成功不能代替这种检查。

本文供设计维护与后续分析使用。运行于其他项目的 Agent 所需的概念与规则，应通过交付的 skill 内容获得，不要求那些项目拥有本文或完整研发资料。

## 十七、后续优化与分析的对照原则

后续机制修订和案例分析，以完整设计意图为参照，同时检查以下关系：

- 通用框架与场景语义是否分清。
- 当前问题是否先被理解，再选择相应处理方式。
- 六个方向是否在选择前逐项认真思考，是否继续识别清单之外的必要责任，未决义务是否保留。
- 实际步骤、Gap 与处理方式是否由分析结果决定，是否以“不固定流程”为由跳过必要工作，或事先排除逐一处理的可能。
- 横向责任与纵向范围是否共同界定 Gap。
- 预期、实现观察、因果结论和过程材料是否分清。
- 实现载体是否按项目维护对象识别。
- 探索是否由关键依据缺失触发，观察是否避免自动成为预期或交付。
- 正式实现是否具备相关预期，局部推进是否尊重真实依赖。
- 重要未知和取舍是否得到独立处理，相关小项是否适度合并。
- 同一 Gap 是否保持事实与决定边界，跨轮是否保持义务连续。
- 新证据是否真正参与重选，而不是只驱动原定实现计划继续。
- 结论是否及时维护，最终完成是否覆盖授权目标内的全部必要责任。
- 新 Agent 是否可以从交付内容理解机制，而不是依赖讨论背景。

这些问题用于判断行为与设计意图是否一致，不规定每项任务必须有多少 Gap、修改多少文档或经历哪些固定阶段。
