# Chat 原生待办能力探索

状态：已采纳（2026-09-19）。正式入口为 [Chat 正式交互原型](../../chat-workspace/default.html)。探索文件保留采纳时的 V4 样本，以下比较过程不覆盖正式交互说明。

探索依据为用户明确纠正后的要求：创建与**当前项目有关**的待办。当前入口为 [Agent 原生交互原型](options/agent-native/default.html)。本轮只重新探索，不修改正式规格或生产实现。

## 核心理解

Chat 是 Agent 的持续对话界面。待办是 Agent 可感知、读取和写入的原生对象。入口负责提交意图或引入对象上下文；语义理解、内容整理与原生能力调用由当前 Chat thread 内的 Agent 完成。

“整体转待办”让当前讨论具有持续待办身份；“对话内新建待办”让 Agent 在当前项目记下另一件事；“已有待办进入 Chat”从对象入口恢复其对话，并读取最新待办事实。这三条路径共用 Chat 的消息、工具活动和 thread 恢复机制。

用户已明确上述能力方向。本候选仅探索具体入口位置、列表呈现、对话反馈与连续性，不把原型当作已采纳产品规格。

## 原型布局

沿用中央 Chat，右侧采用并列的「会话」「待办」标签：同一位置、同一层级，两种索引。待办列表展示当前项目待办，点行直接进入 Chat。两个列表不带来两套消息记录。

标题下显示“本会话对应待办”、身份和业务状态；“查看最新内容”触发 Agent 读取，并在消息中返回目标。输入框只保留发送/停止，分析、执行、创建和更新都由用户的话表达，不要求切换“分析/执行”模式。

自由对话标题旁保留“整理为待办”。输入框使用统一“＋ 能力与引用”入口，分为调用能力（原生能力、Skill）和引用上下文（项目文件、已有待办）。`/` 打开能力候选，`@` 打开上下文候选。选择只添加可移除标签；用户补充内容并发送后才交给 Agent。能力只约束本条请求，引用待办不会切换会话或主待办。

右侧待办列表的加号同样仅把“创建待办”能力放入当前输入框。已输入正文保持。标题旁“整理为待办”是语义完整的直接指令入口；统一选择器中的“整理为待办”则允许用户先补充要求再发送。

选择器为输入框附近的有界弹层，打开时背景不可操作，关闭/Esc 恢复触发焦点。搜索、方向键与 Enter 可选候选，窄窗限制在屏幕内。能力和引用标签随本会话草稿保存；发送后的用户消息保留当时的标签，输入框清空本条选择。

## 三条主路径

### 1. 整段 Chat 整理为待办

用户点击“整理为待办”或在对话中提出要求 → 在当前 thread 出现对应用户意图 → Agent 读取对话和当前项目可用能力，提炼目标及描述 → 原生能力创建待办 → 对话内出现创建回执与轻卡片，待办列表更新。

保留同一 thread、消息和未发送草稿，当前对话关联此待办。用户接着说“按这个继续做”，Agent 在这里读取最新待办并继续推进。创建动作本身不额外启动后台自动执行。

若已有关联待办，“整理为待办”不再创建第二份身份；后续可用自然语言让 Agent 更新当前待办或另建其他待办。

### 2. Chat 内创建当前项目的其他待办

用户直接说“另外帮我记一个待办：给 Chat 增加会话搜索，先记下来，我们继续聊滚动恢复” → Agent 在当前 turn 调用创建能力 → 返回待办卡片，当前讨论继续。

选择“创建待办”能力后，输入想记录的内容，再发送给 Agent。如果只发送能力标签，由 Agent 在对话内询问要记录什么。自然语言直接请求创建仍然有效。

这条新待办保存来源对话关系，不替换当前讨论的主待办，也不因创建而自动开新对话。未来用户主动点击新待办时，再进入该待办关联的 Chat；这一步会保留来源会话的草稿与阅读位置。

Agent 自行发现旁支工作：本候选展示“提出一条有理由的建议 → 用户一句话让它记下 → 调用创建能力”。这是探索中的默认示例；用户已明确授权 Agent 自主记录时，是否直接创建属于后续语义工作流设计，不由原型擅自确立统一审批规则。

### 3. 已有待办进入 Chat 并读写

右侧切到“待办” → 点击一条待办 → 已有关联 Chat 就恢复同一 thread；首次进入则建立对应 Chat，由 Agent 读取待办 → 对话中展示其目标，用户可继续讨论、要求补充内容或执行。

用户输入“补充完成标准” → 用户消息 → Agent 读取最新待办 → 原生能力写回 → 成功回执。再次“查看最新内容”读取修改后的数据，证明待办是活的业务对象，而非首次载入的静态提示词。

用户输入“继续执行” → 同一 Chat thread 内的执行请求 → 读取目标、工具活动、执行结果。原型只模拟反馈，不假装实际运行代码，也不把 Agent 文字回复当作业务完成或验收。

## 同一会话与创建来源

整体整理为待办 T 后，会话列表 A 与待办列表 T 都指向 A 的同一 thread，历史、草稿和执行现场不复制。主标题下标明“本会话对应待办”，列表标明“对应待办 / 当前会话”。

从 A 创建另一条待办 B 时，B 的卡片标明“从本会话创建 · 尚未开始独立对话”。此时仍只有 A；用户主动打开 B 才建立其关联 Chat。进入 B 后显示“创建于：A”的返回入口。来源关系与对应关系不混用。此后再次打开 B 恢复其已有 thread。这是当前候选的具体关系规则，尚未写入正式规格。

## 消息表现的能力边界

| 表现 | 当前依据与候选变化 |
|---|---|
| Agent 文本、工具活动 | 沿用生产 ConversationSurface 已有展示方式；样本文本和工具事件为脚本模拟 |
| 待办原生能力 | Thing 已有能力发现、读取、调用与回执基础；自由 Chat 接入及当前项目独立待办创建仍为新增设计 |
| 待办结果卡片 | 新增候选，由结构化业务回执提供对象身份；不通过识别正文伪造成功 |
| 能力/Skill 选择器与文件/待办引用 | 本轮新增未来输入体验；选中标签不代表已经调用或读过对象 |
| Agent 回复末尾快捷按钮 | 本轮移除。使用正常消息表达补充、执行、接受建议或重试 |
| 原生业务审批 | 生产已有批准请求展示，仍依原有业务契约；与快捷回复、普通消息和引用标签不同 |

原型在独立探索工具区域说明哪些是新增设想；产品区域不把实现说明铺进正常对话。底部场景按钮仅填入样本文字，不是 Agent 生成的按钮。`Skill` 和原生能力在界面中有类型区分，底层不强行统一为同一调用协议。

## 连续性、失败和冲突

- 会话与待办只是两个入口。整体转换及再次进入同一待办不能生成第二条平行执行 thread。
- 来源对话可以创建其他待办；来源 thread 与新待办后续的专属对话关系须可追溯。本轮不将“创建来源”强制等同于“全部后续工作都绑定来源 thread”。此处仍是可讨论的候选设计。
- 创建/写回失败在同一条工具活动中显示失败并保留请求，用户回复“重试刚才的操作”，让 Agent 重试。原型模拟提交前失败；真实幂等、结果未知和部分成功需要单独验证。
- 原生能力回执确认后才更新对象列表。停止只停止当前模拟动作；生产停止不能保证撤销已提交的业务写入。
- 切换列表标签不改变当前对话或草稿。切换对象保存草稿/阅读位置，后台更新不抢选择。
- 已有执行占用、版本冲突、失权或任务删除：后续应通过原生能力返回最新状态，Agent 据此解释和恢复，不能绕开既有 owner 或强行覆盖。本原型未覆盖这些真实异常。
- 正式技术整合需核对 task/session/thread 的持久绑定、当前项目独立待办创建权限与幂等、Agent grant 生命周期、消息/业务事实同步；不能只把 Renderer 卡片接上就声称能力已完成。
