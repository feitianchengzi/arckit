# ArcOrbit：项目、事情与协作的交互探索

状态：候选探索稿，未作为正式交互或产品事实确认。仅修改本目录；不修改生产代码、正式 spec / interaction / tech 或 Runtime。

打开 [index.html](index.html)，进入三份原型。无需构建或启动服务，支持本地文件直接打开。全部业务数据、Agent 回应和执行为固定模拟，没有连接 Workshop、Codex、Runtime、仓库或麦克风。

## 共同的候选交互规则

- 项目提供长期上下文，事情承担目标、归属、状态、结果与协作记录。
- Chat 和 Auto 是推进方式。执行人仍然为人，Auto 不把执行人替换为 Agent。
- 事情的七种业务状态保留；Auto 排队、运行、暂停、等待决定和失败是额外执行状态，不直接替换业务状态。
- 默认展示工作现场，完整消息仅在主动“查看消息”“交流”或“暂停并讨论”后展开。
- 底部轻量输入框持续可用。发送文字后可以只更新分析、工作内容或待生效说明，无需显示整个聊天窗口。
- 无现成待办时，通过“发起事情”发送第一条有效内容，同时建立一件执行人为自己的待评审事情。发起不会启动 Auto，不增加第二份待办。
- 显示项目选择，首条提交前允许修改。项目与本机执行资格各自明确；不得从“所有项目”隐式选择错误的执行范围。
- 对话创建的待评审事情不进入自动领取。启动 Auto 的动作明确完成目标确认并申请执行；直接启动不隐式开启全局自动领取。
- 已有事情可以直接 Auto，也可以先分析、修正目标、继续交流，再 Auto。原型的协作身份保持不变，模拟未来同一事情的语义连续性。
- 人工修改目标直接更新同一事情内容，后续 Agent 使用该目标；草稿与消息逐事情隔离。
- 运行中“追加说明”立即接收，在下一执行边界生效，运行保持继续。需要马上调整方向时，使用“暂停并讨论”，停止当前推进后交流，再显式恢复。
- 打开消息、切换项目、切换事情和收起交流都不停止后台执行。
- 停止执行不等于完成或取消事情；恢复使用原事情的协作身份。
- 验收问题独立记录，未解决时阻止验收通过。原事情的已完成结果保持可查。
- 语音入口只说明后续位置。本轮不录音、不转写、不播报。未来输入、播报与停止执行分别控制。
- 生命周期保留在“资料与专业视图”。打开专业视图只切换观察或操作内容，不隐式改变阶段、业务状态或授权。

## 推荐体验路径

每份方案都使用同样的路径，避免不同样例影响比较。

1. **已有事情直接 Auto**：打开 #101“优化事情列表的键盘导航”，选择“开始 Auto”，核对目标和执行人并开始。查看其进入 Auto，执行人保持为自己。到“演示控制”点击“推进一个执行步骤”观看进展。
2. **先 Chat 再 Auto**：打开 #102“整理离线恢复方案”，点击“先分析”。分析出现在现场，消息默认隐藏。编辑目标或继续输入要求，再开始 Auto。如果 #101 仍占用 ArcOrbit 工作区，#102 排队等待。
3. **没有现成事情**：点击“发起事情”，选择项目、输入内容并“发起并交流”。页面进入新事情现场，执行人为自己、状态为待评审。继续输入不会再创建事情。
4. **Auto 中介入**：打开 #103“修复反馈图片加载”。直接输入要求并发送，观察待生效说明；推进一次模拟步骤，说明生效。再点击“暂停并讨论”，在主动打开的交流中补充，点击“继续 Auto”。
5. **处理 Agent 请求的决定**：打开 #104，现场直接给出待决定问题。选择方案后继续执行；也可先讨论，不因讨论而自动解除决定。
6. **检查结果**：打开 #105，查看成果，提出验收问题，观察已完成结果保持、验收按钮禁用。点击明确标注的“模拟解决”后完成验收。
7. **失败与恢复**：演示控制启用“下次提交失败”，发起一件事情。检查内容保留且没有创建重复记录，重试后仅新增一件。离线开关可检查发送失败后草稿保留。
8. **恢复现场**：在事情 A 输入未发送内容，切到 B，再返回；刷新页面后继续。完整 Chat 恢复为隐藏状态，事情与草稿保留。

自动执行由“推进一个执行步骤”驱动，不伪造真实后台耗时。模拟全局自动领取只有开启后才在该步骤中消费待处理候选；同项目排队、跨项目执行采用简化模型。

| 自动领取、项目准备、工作区并发、排队 | 执行与连接 / 事情状态 | 简化可交互模型；认证、安装、所有权与租约未接入 |

| 主动介入、人工决定、暂停、继续、停止、恢复 | 原事情现场与按需交流 | 主路径可交互；真实运行边界、持久线程恢复需架构验证 |
| 外部等待、启动失败、状态冲突恢复 | 事情现场的原因与恢复入口 | 模拟执行中断和字段变更后的核对；完整故障矩阵未模拟 |
| 成果审查、独立验收问题、验收通过 | 成果与验收 | 可交互模拟；独立问题队列执行未模拟 |
| CLI 接管、Git 交付 | 执行详情 / 专业视图 | 入口映射，未模拟 |
| Work Sync、分页、鉴权、并发冲突、幂等写入 | 现有事实 owner 与业务服务 | 未接入；原型的本机保存不证明后端契约已成立 |

## 需要后续解决的架构与迁移问题

现有 Chat 与 Automation session 边界明确分离，当前 Chat 规范也不自动创建 Workshop 事情。本稿是用户要求的新方向，不能靠把两个已有页面拼在一起实现。

- 新事情如何绑定首条 Chat、正式待办与持久 Agent thread，创建/绑定部分失败时如何恢复。
- Chat → Auto 如何续接相同语义上下文、重新核对授权与工作区，避免额外创建第二个 Agent 执行线程。
- Auto 正在执行时补充输入如何安全送达，以及暂停确认前/后对消息生效状态的精确表达。
- 无项目的初步交流如何暂存，何时绑定正式项目；本原型先要求显式项目，不创建假项目。
- 历史自由会话如何保留、关联或迁移，不能自动把历史全部变成团队待办。
- 创建待办的可见性与团队范围如何展示；本机演示不代表正式消息、草稿和待办都能跨设备同步。
- 人修改目标与 Agent 晚到建议的修订冲突；本轮只有同步模拟，不声称已解决并发编辑。
- 与 Today 的跨项目责任聚合如何合并入口，同时保持来源对象和决定身份唯一。
