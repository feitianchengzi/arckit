# 软件 Gap：把概念用于一个任务

首次使用软件场景定义时读取；需要区分取证与正式结论、常规排障与独立诊断时回看。规则来自随包的 [场景定义](../templates/software-state-definition.json) 和当前 Project 不变量；以下情境帮助理解，不是固定执行顺序或预设 Gap 清单。

## 先分清五件事

| 概念 | 要回答的问题 | 同一导出需求中的含义 |
| --- | --- | --- |
| 不变量责任 | 哪些条件应成立，须用什么证据支持？ | 技术选择有依据，相关预期可恢复，实际行为兑现预期 |
| 纵向范围 | 本次判断覆盖什么对象？ | 当前权限下、当前筛选结果的十万条订单导出 |
| 事实角色 | 材料说明应该怎样、实际怎样，还是为何发生？ | “支持十万条”是预期；实验资源记录是观察；超限原因是因果结论 |
| 结论性质 | 本轮验收取证结果，还是有依据的正式决定或兑现？ | 接受实验记录不等于正式采用方案；确立方案也不等于功能可用 |
| Gap | 当前哪个具体结果尚未成立？ | 缺少大数据量可行性证据，或缺少明确行为，或尚未兑现已定行为 |

事实角色按材料用途判断，结论性质按本轮验收判断。同一不变量可以涉及探索和正式结论；同一 Gap 可以涉及多个责任，但须共享目标、前提与验收边界。Case 保存整个授权目标及已知义务，Loop 推进一个选定 Gap 后重新判断。

## 新需求：十万条订单导出

假设用户要求“导出当前筛选结果，支持十万条，等待期间页面仍可操作”。项目已有有效的权限规则、视觉组件及异步任务框架，导出组件能否满足资源约束尚无证据。

先从全部责任考虑：产品和交互行为尚需明确，技术可行性可能影响决定，实现尚未完成；视觉核对后复用已有规则，没有故障证据时说明诊断不相关。未选中的已知义务保持开放，不按责任数量生成六个 Gap。

下面是一条假设实验可行的分支，每次均依据新事实重新比较：

| 当前选择 | 验收证据与接受结果 | 仍未成立的主张 |
| --- | --- | --- |
| 取得限定资源下十万条导出的可行性证据 | 可修改真实实现载体进行实验，记录输入、条件、资源与结果；接受证据支持的可行性结论 | 未正式采用该方案，未确定全部相关行为，也未完成交付 |
| 确立本次导出的行为与接入约定 | 在授权内确定等待、成功、失败等行为，维护相应预期事实；共同决定的相关小项可合并 | 正式实现仍待选择；出现独立重要架构或权限取舍时另行比较 |
| 兑现已接受的导出预期 | 可复用实验代码，按正式预期验证筛选、权限、交互与资源约束；接口、界面和测试共同证明结果 | 证据不足保留同一 Gap；不能因实验产物已存在宣称完成 |
| 普通义务闭合后的完成复审 | 按授权目标检查正确性、问题解决、验证可信度、回归和最小性 | 不把局部导出结果扩展为整个产品无缺口 |

若实验可靠地证明不可行，该取证 Gap 可以完成；它使替代方案或有权责任方的需求取舍成为候选，不允许自行降低十万条要求。若实验根本没回答问题，则保留原 Gap 与已有证据。若进入任务时已有充分可行性证据和有效预期，可直接选择实现，不重走示例各行。

范围与责任不能混淆：另一个模块的独立未决预期不阻止此处推进；共享权限契约未定则阻止依赖它的正式实现。实验观察是真实实现侧证据，但它只证明声明条件内实际发生了什么。

## 执行中：继续还是重选

| 新情况 | 对当前 Gap 的处理 |
| --- | --- |
| 接口完成，开始界面联调 | 同一验收内的动作依赖就绪，继续当前结果 |
| 为满足既定资源约束调整内部批次，正式约定未变 | 属于实现手段调整，继续验证；若批次本身是已接受契约，则先重审该预期 |
| 当前结果验证中测试失败，排障仍用于证明同一约定 | 可以继续常规定位、修正和验证；不因一次失败自动创建诊断 Gap |
| 证据暴露独立的重要原因未知，或否定当前资源/权限等关键前提 | 保存证据和未完成义务，提交并重新选择；不能以“实现中排障”为由包揽 |
| 为使测试通过，需要改变产品行为或验收标准 | 重审预期，不能在当前实现 Gap 顺带修改预期再宣称兑现 |

判断依据是问题是否形成独立的重要因果判断、是否改变已接受预期或当前前提与验收边界，不是报错数量、文件数量、耗时或是否处于实现阶段。

## Bug：导出按钮点击无效

用户待解决的故障直接原因未知时，先选择诊断。假设复现和源码证据表明事件处理器未绑定：接受这一因果结论并提交，fresh-read 后再比较处置；相关预期有效且充分时直接修复，不另造产品、交互或技术文档修改轮次。

如果原因实际是权限拒绝，不能仅为消除症状而绕过权限：根据有效的权限与反馈预期判断缺少的结果。若用户已提供可靠直接原因证据，复用证据直接比较修复工作。原因已知不代表预期有误，也不代表修复已经完成。

该规则同样适用于维护 skill：SKILL.md、脚本与模板可以是实现载体，能力规格是预期；试跑观察、正式采用某条指令及其行为兑现分别需要相应依据，不由 Markdown 格式决定事实角色。
