# 智能客服信息架构系统性重设计

> 文档日期：2026-09-19
>
> 动机：迭代过程中界面能力以增量补丁方式落位（先在反馈详情、后挪控制轨、再补 Organization），缺乏从业务场景与产品目标出发的系统性推导，导致出现"作用域错位"（项目级配置嵌入单反馈视图）等返工。本文以业务场景清单与对象作用域模型为第一性依据，一次性定义智能客服相关能力在客户端的完整落位，并给出迁移清单。后续新增能力按本文规则落位，不再逐案拍板。
>
> 依据文档：[`customer-support-prd.md`](./customer-support-prd.md)（产品目标与功能清单）、[`customer-support-orchestration-plan.md`](../../产品规划/customer-support-orchestration-plan.md)（治理层/执行层边界）、[`../../现状梳理/01-product-architecture.md`](../../现状梳理/01-product-architecture.md)（页面产品角色基线）。

## 一、产品目标与设计原则

### 1.1 产品目标约束

- 核心命题：验证 arc 需求开发 loop 能在真实客户仓库上端到端跑到可交付产物。
- 智能客服是**对客统一出入口**，不是独立产品；它由「两层知识库检索 + 分级应答」支撑。
- 单客户试点：不做多租户、自动分配、capabilities 细粒度（role 兜底）。

### 1.2 设计原则（落位的唯一依据）

| # | 原则 | 含义 |
|---|------|------|
| P1 | **作用域决定落位** | 对象的作用域（组织/项目/反馈/任务）决定它出现在哪些界面、可在哪里配置。作用域不匹配即错位，无论技术上多方便 |
| P2 | **配置权威面唯一，引用面多处** | 每个可配置对象只有一个权威配置面（完整 CRUD）；其他界面只放只读状态或跳转入口，触发的是同一个配置组件 |
| P3 | **能力跟随业务域页面** | Organization 管治理（人、授权、项目生命周期），Feedback 管反馈运营（处理、进展同步），Work/Command 管执行。配置放使用它的业务域，状态引用放治理页 |
| P4 | **组件与令牌复用既有体系** | 新界面只允许组合既有组件模式（section-title-row 图标头、status-pill、data-table、fact-row、release-dialog、卡片骨架）与既有 token（type/radius/成对色板），不发明新样式 |

## 二、业务场景清单（场景 → 能力 → 界面）

| 场景 | 描述 | 需要的能力 | 承载界面 |
|------|------|-----------|---------|
| S1 新客户接入 | 管理员为新项目做运营准备：登记代码仓库、建索引、验证检索 | 项目级知识库配置（CRUD/同步/**检索测试**） | **Organization → 项目 → 配置知识库**（权威面）；Feedback 控制轨同组件入口 |
| S2 客户提问 | 客户在 SDK 提问，两层检索分级应答（高置信直答/中置信草稿/低置信转收集） | 检索 + 分级策略（运行时行为） | SDK 侧；客户端无配置 UI（策略随部署） |
| S3 客户提交反馈 | 对话收集位置/现象/期望 → 结构化反馈入站 | 反馈通道 | SDK 侧；入站后进 Feedback 收件箱 |
| S4 反馈分诊 | 处理人查看 AI 初判 → 人工确认/调整 → 转待办 | 分诊初判展示、采纳/调整、convert-to-task | **Feedback 详情**（单反馈作用域） |
| S5 处理中检索溯源 | 处理人查看该反馈的检索命中与置信度 | 检索卡片（该反馈自己的数据） | **Feedback 详情** |
| S6 Loop 执行与客户追问 | Codex loop 开发；客户追问经桥3 steer 注入同一线程 | steer 硬关联门控（运行时行为） | Work/Command 态势；追问注入为事件，无需 UI |
| S7 进展同步 | closeout 生成草稿 → 处理人确认/驳回 → 客户可见 | 草稿确认流 | **Feedback 详情**对话区（draft-confirm 气泡） |
| S8 验收交付 | accept → 构建产物 → artifact_url 回写 → 客户通知 | 产物交付回写、状态时间线 | Work/Task 检查器（artifact 展示）+ Feedback 时间线 |
| S9 检索没命中排查 | 反馈处理时发现检索空白 → 定位是索引缺失 | **检索测试**（直查索引命中） | 项目知识库配置弹窗内 |

**场景推导结论**：知识库相关能力只服务 S1/S5/S9 三个场景，全部是**项目作用域**；反馈详情内的四个区块（初判/检索卡/草稿/对话）全部是**反馈作用域**。两类作用域不得混排——这就是此前"作用域错位"的判定依据。

## 三、对象作用域模型（P1 落位规则表）

| 对象 | 作用域 | 权威配置面 | 主展示面 | 只读引用面 |
|------|--------|-----------|---------|-----------|
| Feedback / FeedbackMessage | 反馈 | —（不可配置） | Feedback 详情 | Today 责任台 |
| 分诊初判（data.triage） | 反馈 | —（后端自动生成） | Feedback 详情 | — |
| 检索命中（retrieval） | 反馈 | — | Feedback 详情检索卡片 | — |
| 进展草稿（pending_review message） | 反馈 | — | Feedback 详情对话区 | — |
| Task / Case / artifact_url | 任务 | — | Work / Command / Task 检查器 | Feedback 时间线 |
| **CustomerCodeRepo / KnowledgeSource / CodeChunk** | **项目** | **Organization → 项目 → 配置知识库弹窗** | 同左（弹窗内面板） | Feedback 控制轨入口（同组件） |
| OpenHands Agent 配置（阈值/Persona） | 项目 | 部署阶段定（API 已备） | — | — |
| Organization / Member / Role / Workset | 组织 | Organization | Organization | — |

**规则**：任何新能力先回答"对象挂在哪个 id 下"，再按本表落位。反馈详情永远不出现项目作用域配置；Organization 永远不出现反馈处理动作。

## 四、组件规范（P4 约束）

| 组件 | 既有模式 | 使用处 |
|------|---------|--------|
| 详情页区块骨架 | 白卡 + ink-150 边 + 9px 圆角 + block-end 14px | 初判/检索卡/仓库面板 |
| 区块头 | `.section-title-row` + `.section-icon`（28px violet chip）+ h2(type-body) + p(type-caption) | 所有面板头 |
| 语义药丸 | `.status-pill` 尺寸体系 + 成对色板（green/amber/red/violet/blue） | 置信度、仓库状态、草稿状态 |
| 数据表 | `.data-table`（th 微大写灰底） | 仓库列表 |
| 弹窗 | `.release-dialog` + form method=dialog + showModal | 添加仓库、知识库配置 |
| 事实行 | `.fact-row` / 灰底小卡（7px 圆角） | 初判字段、连接状态行 |
| 引用条 | 左 3px violet 边 + violet-50 底 | 拟回复、推理说明 |
| 字号/字重/圆角 | `--type-*` 全覆盖；字重 750/800/850；`--radius-sm/md/lg` | 一律，不得裸 px/hex |

## 六、边界（明确不做）

- 反馈详情不放任何项目级配置；Organization 不放反馈处理动作。
- 不做知识库批量导入、不做多租户知识库隔离（单客户试点）。
- 检索分级策略（0.75/0.9 阈值）不提供 UI——初期人工拍保守值，属部署配置（PRD Q-03）。
