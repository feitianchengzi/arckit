# 客户支持通道 — 生产部署文档

> 本文档指导"客户支持通道"迭代投产到生产环境。每一步标注**做什么**、**怎么做**、**验收标准**。代码已 100% 完成(见 `迭代总结.md`、`implementation-handoff.md`),部署只涉及基础设施与配置上线。

## 0. 前置依赖清单

生产环境必须先具备以下基础设施。**缺一项链路可能降级但不一定断裂**——三个外部依赖均有降级策略,但为完整能力建议全部就绪。

| 依赖 | 用途 | 缺失影响 | 降级策略 |
|---|---|---|---|
| PostgreSQL 12+ | 反馈/消息/通知/分诊/Agent 会话持久化 | 服务无法启动 | 无降级,必须就绪 |
| API 网关 | 统一认证(JWT/APIKey)、注入 X-User-ID、签发/校验 feedback session token、转发请求 | SDK 无法鉴权 | 无降级,必须就绪 |
| 阿里云 OSS/STS | 反馈附件上传与访问 | 附件功能不可用 | 文本反馈仍可用,附件报错 |
| OpenHands Agent Server | 智能客服基于代码仓库的问答 | 智能客服转人工兜底 | Agent 不可用时智能客服降级提示,不阻断反馈提交 |
| Embedding BGE-M3 服务 | 代码语义检索(RAG) | 代码语义检索不可用 | 退化为关键词检索,Agent 仍可直读代码 |
| LLM API(经 OpenHands 调用) | Agent 推理 | Agent 无法生成回复 | 智能客服降级提示 |
| CORS/Origin 白名单 | SDK iframe 跨域 | SDK 无法 postMessage | 必须配置含 SDK 域名 |
| 网关 WS 透传 | V2 WebSocket 实时推送 | 无实时推送,SDK 退化为轮询 | 必须支持 WS Upgrade + Sec-WebSocket-Protocol 透传 |

### 0.1 网关专项要求(本轮新增 V2 WS)

- **session token 签发**:网关或宿主后端用 API Key 调 `POST /workshop/v2/apikey/feedback-sessions` 换取 15 分钟 `fbs_` token 下发客户端。
- **session scope 注入**:网关校验 `fbs_` token 后注入 `X-Auth-Type: feedback_session` + `X-Feedback-Gateway-Secret`(与 workshop `FEEDBACK_GATEWAY_SHARED_SECRET` 一致)+ `X-Feedback-Project-ID` / `X-Feedback-Custom-User-ID` / `X-Feedback-Session-ID`。
- **WS 透传**:V2 SDK 通过 `wss://<gateway>/workshop/v2/feedback/projects/:id/ws` 连接,token 走 `Sec-WebSocket-Protocol: nebula-auth.<token>`。网关必须**透传 subprotocol 字段**并支持 WS Upgrade,不能剥离 `Sec-WebSocket-Protocol`。
- **`FEEDBACK_SESSION_SIGNING_KEY` 与 `FEEDBACK_GATEWAY_SHARED_SECRET`**:网关与 workshop-api 必须使用相同值,且两者是**不同**的密钥(见 `env.workshop.production.example:73-76`),用 `openssl rand -base64 48` 生成,≥32 字节,不提交。

## 1. 后端 workshop-api 部署

### 步骤 1.1 准备环境变量
**做什么**:基于示例生成生产 env。
**怎么做**:
```bash
cd services/workshop-api/deploy/prod
cp env.workshop.production.example .env.workshop.production
# 编辑 .env.workshop.production,填写实际值:
# - DB_* :RDS 连接
# - CORS_ALLOW_ORIGINS :生产域名(含 SDK 域名、Console 域名)
# - OSS_* :阿里云 OSS AccessKey/Secret/Region/Bucket/RAM Role ARN/RootPath
# - FEEDBACK_SESSION_SIGNING_KEY :openssl rand -base64 48
# - FEEDBACK_GATEWAY_SHARED_SECRET :与网关一致,另生成一个
# - FEEDBACK_NOTIFICATION_SHARED_SECRET / NOTIFICATION_INTERNAL_SHARED_SECRET
# - LLM_BASE_URL / LLM_MODEL(给 OpenHands)
# - LLM_API_KEY 可在首次展示部署时留空；项目 owner/admin 可之后在 Feedback Console 保存项目 Key
```
**验收标准**:`.env.workshop.production` 中除允许留空的 `LLM_API_KEY` 外，所有 `REPLACE_WITH_*` 已替换为实际值;密钥均 ≥32 字节且未提交 Git(`git status` 不显示该文件)。项目 Key 和服务器 Key 都未配置时，智能客服自动使用本地索引降级链路。

### 步骤 1.2 构建并启动 workshop-api
**做什么**:构建镜像、启动服务。
**怎么做**:
```bash
cd services/workshop-api/deploy/prod
docker compose -f docker-compose.prod.yml build
docker compose -f docker-compose.prod.yml up -d
```
**验收标准**:
- `docker compose -f docker-compose.prod.yml ps` 中 todo-service 状态 `Up`。
- `curl https://<gateway>/workshop/v1/public/health` 返回 200。
- 容器日志无 `FEEDBACK_SESSION_SIGNING_KEY 未配置` 等报错。

### 步骤 1.3 执行数据库迁移
**做什么**:应用 schema 变更。生产部署脚本先在 `DEPLOY_BACKUP_DIR`（默认 `/opt/todo/backups`）生成并校验 PostgreSQL custom-format 备份，再在切换服务前运行候选镜像的统一迁移入口，其中已内嵌智能客服 4 份幂等 SQL。
**怎么做**:
```bash
# 生产由 remote-deploy.sh 自动执行；手工预检时使用同一条命令。
./todo migrate
```
**验收标准**:
- 迁移无报错退出。
- `\dt` 存在 `feedbacks`、`feedback_messages`、`feedback_notifications`、`openhands_agents`、`customer_code_repos`、`agent_conversations`、`agent_message_records` 等表。
- `OPENHANDS_ENABLED=true` 时服务启动还会校验上述表和关键列；缺失时拒绝接流量。

### 步骤 1.4 部署 OpenHands Agent Server(智能客服依赖)
**做什么**:启动 OpenHands Agent 容器，与 workshop-api 共享代码副本卷。

智能客服有两个生效档位：
- **档位 A（本地索引）**：不部署 OpenHands，`OPENHANDS_ENABLED=false`，智能客服只检索代码片段（无 LLM 推理，置信度 0.7）。适合验证链路。
- **档位 B（OpenHands Agent，生产推荐）**：LLM 基于代码实时推理，带置信度自评 + 低置信结构化总结。需部署 OpenHands + 配 LLM env。

**怎么做**（档位 B）:
```bash
cd /opt/todo/deploy/prod
# 先配置固定 digest、OpenHands 密钥、项目配置加密密钥和共享目录；LLM Key 可后配。
# 当前小规格服务器还必须先提供至少 2 GiB Swap。
./openhands-control.sh preflight
./openhands-control.sh start
```

**容器卷对齐**（关键）：workshop-api 和 OpenHands 容器必须挂载同一个宿主目录到相同的 `/workspace/customer-repos` 路径，否则数据库中的 `repo_path` 对 OpenHands 不可见：
```yaml
services:
  todo-service:
    volumes:
      - /opt/todo/customer-repos:/workspace/customer-repos
  openhands-agent:
    volumes:
      - /opt/todo/customer-repos:/workspace/customer-repos:ro
```
Workshop 负责 clone/pull；OpenHands 只读代码。两个容器通过补充组 `OH_SHARED_GID` 访问宿主目录。OpenHands 不映射公网 8000 端口，只允许 `workshop` Docker 网络访问。

**验收标准**:
- `curl http://<openhands-host>:8000/health` 返回 200。
- `GET /workshop/v2/user/projects/:id/openhands-health` 返回 healthy。
- 两个容器挂载同一 `customer-repos` 卷，workshop-api clone 进去的代码 OpenHands 能读。

### 步骤 1.5 配置客户项目 OpenHands 与知识源
**做什么**:为每个客户项目配置 OpenHands agent 与代码仓库（智能客服的代码源）。
**怎么做**:项目 owner/admin 在 Feedback Console 的「接入设置 → V3 智能客服（验证版）」中保存项目自己的模型 Key。明文仅在本次 HTTPS 请求中传输，后端加密落库且不再回显；保存后无需重启或重发 SDK。服务器 `LLM_API_KEY` 仅作项目未配置时的全局兜底。

等价 API 配置（仅用于运维调试）:
```bash
# 1. 配 OpenHands agent
PUT /workshop/v2/user/projects/:id/openhands-config
# body: { "url":"http://openhands-agent:8000", "llm_model":"deepseek/deepseek-chat", "llm_base_url":"https://api.deepseek.com", "llm_api_key":"<PROJECT_LLM_KEY>" }
# 响应只返回 llm_api_key_configured / llm_api_key_source，不返回明文或密文。

# 2. 配代码仓库（GitHub URL，clone 到 {OH_REPO_ROOT}/{projectId}）
POST /workshop/v2/user/projects/:id/code-repos
# body: { "customer_id":"<customUserId>", "repo_url":"https://github.com/org/repo.git", "branch":"main", "auto_sync":true }

# 3. 触发 sync（clone + 索引）
POST /workshop/v2/user/projects/:id/code-repos/:repoId/sync
```
sync 成功后 `runCodeIndexPipeline` 自动建索引。验证：`SELECT status FROM knowledge_sources WHERE name='code-repo-<repoId>'`，期望 `synced`。

> **客户端组织页配置 ≠ 智能客服代码源**：桌面端组织页的"选择本地目录"/"Git 地址"写入 `project_bindings`（arcorbit runtime），服务于本地 Automation/Chat，**不进 `customer_code_repos`，智能客服读不到**。两者是独立配置，不能互相替代。智能客服的代码源必须通过上述 API 配 `customer_code_repos`。
>
> **本地目录在生产不可用**：`repo_path` 指客户端本地路径，生产服务器上不存在，`dirExists` 返回 false，Agent 看不到代码。生产必须用 `repo_url` + sync，clone 到服务端 `OH_REPO_ROOT`。

**验收标准**:
- `GET /workshop/v2/user/projects/:id/openhands-health` 返回 healthy。
- `GET /workshop/v2/user/projects/:id/knowledge/code-stats` 显示代码 chunk 已索引。
- `POST /workshop/v2/user/projects/:id/knowledge/retrieve-test` 能检索到代码片段。

## 2. SDK 构建与部署

### 步骤 2.1 构建不可变 SDK release
**做什么**:构建带版本号的 SDK SPA；V1/V2 是接入协议，不再等于可覆盖的静态目录版本。
**怎么做**:
```bash
cd apps/feedback-sdk-web
npm run build:release -- 2.0.0-canary.20261014
```
**验收标准**:
- `tsc` 无类型错误。
- `dist/index.html` 与 `dist/assets/*` 生成。
- 产物中不含硬编码 `api.feitianchengzi.com`(本轮已移除该 fallback)。

### 步骤 2.2 发布 release 并切换灰度通道
**做什么**:先上传不可变产物，再让独立 canary 入口指向它；不覆盖 `/sdk` 或 `/sdk-v2`。
**怎么做**:
```bash
cd apps/feedback-sdk-web
python3 scripts/sdk_release.py publish --version 2.0.0-canary.20261014 \
  --dist-dir dist --env-file .env --compatible-contracts v1,v2 \
  --source-commit "$(git rev-parse HEAD)"
python3 scripts/sdk_release.py promote --version 2.0.0-canary.20261014 \
  --channel canary --env-file .env --alias sdk-v2-canary:v2 \
  --confirm-promote canary:2.0.0-canary.20261014
```
**验收标准**:
- `https://<sdk-host>/sdk-v2-canary/index.html` 跳转到对应不可变 release。
- `/sdk` 和 `/sdk-v2` 的线上 hash 保持不变。
- V3 验收通过后只更新 `stable` channel；回滚时把它指回旧 release。

## 5. 端到端验收(投产后)

按以下顺序逐项验证,全部通过方可宣告投产完成。

### 5.1 SDK 集成与身份
**做什么**:宿主前端/移动端用 iframe/WebView 嵌入 SDK,session 模式注入 `fbs_` token。
**验收标准**:
- 客户提交反馈 → 生成 Feedback,编号回显。
- 同一 `project_id` 不同 `custom_user_id` 的反馈互相隔离(客户 A 看不到客户 B 的反馈)。
- session token 过期后 SDK 触发 `feedback-sdk:refresh-session`,宿主刷新后恢复。

### 5.2 智能客服
**做什么**:客户在对话窗口提问。
**验收标准**:
- Agent 基于代码仓库回复，显示置信度。
- session 模式下 Agent 对话可用（本轮修复的 bug）。
- **对话窗口无转人工入口**（本轮移除）。
- **对话窗口支持上传图片**（选择/预览/发送）；`AGENT_VISION_ENABLED=true` 且多模态模型时 Agent 能看图回复。
- Agent 不可用时降级提示，不阻断反馈提交。
- **低置信（<0.75）时触发结构化预填**：Agent 回复末尾带 `[summary]` 结构化总结，后端解析后前端预填反馈表单（位置/现象/期望三字段）；模型未给出总结时退回提问原文。
- **降级路径（本地索引）置信度一致**：本地索引有结果时 confidence 0.7 < 0.75 阈值，也触发 NeedCollect，与 OpenHands 路径行为一致（本轮修复）。

### 5.3 客服回复→客户面板消息
**做什么**:客服在 Console/Desktop 反馈详情页回复。
**验收标准**:
- 客户在对话窗口时:新消息向上推显示(自动滚动到底),无需手动刷新。
- 客户不在对话窗口时:SDK 展示未读红点(`feedback-sdk:unread-changed`);Desktop 客服侧非当前反馈 toast + badge。
- 外部 iframe 宿主收到 `feedback-sdk:unread-changed` 并展示红点。

### 5.4 实时通道
**验收标准**:
- SDK 连接 V2 WS 后 `已连接实时推送` 提示出现(`SDKStatusPage` 的 connected 状态)。
- 客服回复后 1s 内客户端收到新消息(WS 推送),而非等 30s 轮询。

### 5.5 全链路
**验收标准**(对应 PRD US-01~US-09):
- 客户对话反馈→确认提交生成 Feedback(US-01)。
- 我的反馈显示状态时间线(US-02)。
- 内部分诊门控可转 Task 或忽略(US-04)。
- Task 认领进 Codex loop(US-05)。
- 进展草稿确认后发客户(US-06)。
- 验收后构建产物,artifact_url 回写,客户可见(US-07)。

### 5.6 i18n(本轮新增)
**验收标准**:`window.FeedbackSDK.setLocale('en-US')` 后 SDK 文案切换为英文;`configure({ locale: 'zh-CN' })` 切回中文。

## 6. 回滚预案

- **后端**:`remote-deploy.sh` 在健康检查失败时只重建 `todo-service` 并恢复上一镜像，不停止 OpenHands；数据库迁移均为 additive，若需数据级恢复，使用该次发布前已校验的 `.dump` 备份并先评估影响。
- **SDK**:不覆盖不可变的 `/sdk-releases/<version>/`；把对应 channel 重新 `promote` 到上一 release 即可回滚。
- **Desktop**:分发上一安装包版本。
- **网关 V2 WS**:若 WS 透传有问题,SDK 自动退化为 30s 轮询,链路不断(功能降级而非中断)。
