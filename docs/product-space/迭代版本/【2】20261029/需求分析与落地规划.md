# 多模态智能客服与反馈体验：需求分析及落地规划

> Proposed / 2026-10-29。本文沉淀当前代码检查结果和建议方案，设计稿是模拟交互，不连接后端或真实模型。

## 1. 目标与边界

让用户用文字、截图及语音说明问题，模型能够真实理解媒体；每一次反馈都能完整追溯沟通、处理过程和结论，支持问题检索及时间筛选。复用现有 Session、澄清、确认建卡、任务推进和交付回写，不自动替团队决定受理、优先级及排期。

## 2. 当前链路

外部宿主后端换取短期 Session → iframe/WebView configure → 独立客服会话 → 本地正向白名单或 OpenHands 项目知识问答 → 未解决时多轮澄清 → 客户核对、编辑并确认结构化草稿 → 创建反馈并关联原会话 → 团队回复、受理转待办 → 任务状态与交付回写 → 客户查询及继续补充。

SDK 是部署式 SPA，不是 npm UI 组件。Session 是推荐外部接入方式。WebSocket 发送最小变更事件，客户端经鉴权读取正文。

## 4. 页面现状与方向

正式SDK采用卡片、主题令牌及移动端列表/详情切换；演示站独立 chat-widget.html 已绕开旧iframe，不能视为正式SDK。建议演示站统一加载正式SDK。

现状问题：状态页外宽980px但embed壳640px，分栏依据视口而非容器；多层滚动；移动端默认第一条详情；展示连接状态和模型置信度，业务价值不清晰。改为容器响应式、桌面列表+更宽详情、移动端列表进入详情、固定输入区与安全区适配。

一级入口：我的反馈、智能客服。我的反馈提供搜索、时间、状态、未读筛选；详情提供概览、沟通记录、处理进展、结论与交付。咨询保留独立历史，未建卡咨询不自动变为正式反馈。

## 5. 图片理解

选图/拖拽/粘贴 → 预览压缩 → 服务端授权上传 → 完成登记 → 消息引用attachment_id → 客户及会话归属校验 → 临时模型读取资源 → 原生视觉理解结合项目知识 → 保存回答和证据。

稳定存object_key，推理时生成短期读取资源；不信任任意外部URL。检查真实文件格式、像素、大小、归属和完成状态。首轮、续轮、重建均支持媒体；历史可预览与追问。带附件时不能被问候白名单提前截断。

OCR只是辅助，不能代替视觉理解。回答区分直接观察、资料解释与待验证假设。建议首版每轮4图、单图10MB、总20MB，实际限制待实模评估。图片生成结构化字段应引用来源图和消息，不能当作用户已经确认的事实。

## 6. 语音理解

主路径采用原生音频输入模型；ASR→文本模型仅作显式降级。首版分段录音：申请权限→录音→停止/取消→试听→上传→音频理解→转写及文字回答。建议上限60秒；支持图片与音频组合。转写可纠正但保留原文，版本号、金额、错误码再次确认。不自动播放回答，不按语气判优先级。

Web要求HTTPS、iframe allow microphone和宿主Permissions Policy；iOS/Android处理原生权限、WebView授权、切后台和格式差异。录音格式由服务端归一化。增加原生录音bridge；权限拒绝时保留文字入口。

适配层声明image_input/audio_input/audio_output/streaming能力并真实探测。验证OpenHands音频契约；不支持时增加媒体理解适配器，将带证据的结果交给现有客服。实时双向语音、打断和TTS放后续阶段。

## 7. 历史、检索与结论

统一记录覆盖原咨询、AI回复、客户确认、人工回复、附件、音频及转写。使用来源ID去重，不以正文相同判断重复。消息采用游标分页；新消息不强行打断用户阅读旧记录，提示有新消息。已读回执绑定实际读到的消息边界。

结论独立版本化：类型、正文、来源（AI建议/人工确认/正式交付）、发布人、时间、适用版本、证据、交付链接、客户确认情况。状态为草稿/已发布/被替代。问题草稿不等于结论；答复、交付、客户确认解决分别表达。新增证据冲突时标记需复核，不覆盖历史。

搜索默认编号、标题、描述，可扩展沟通、转写、已发布结论。服务端返回片段及定位ID。时间默认提交时间，可切最近沟通时间；用户本地日期转换UTC半开区间。权限范围先于查询。优先PostgreSQL，按中文质量和规模评估trigram/分词，暂不引入独立搜索集群。

## 8. 技术拆分

- SDK：通用媒体输入、预览、录音、统一详情、分页、搜索筛选、容器响应式。
- 消息：客户端幂等ID、稳定服务端ID、附件引用、状态；旧metadata兼容读取。
- 附件：统一归属、大小/格式/时长/尺寸、完成状态及授权读取。
- 模型：统一消息构造、能力校验、超时、明确降级，记录媒体是否实际被处理。
- API：扩展现有列表查询q/date_from/date_to/status/cursor；统一会话分页；结论查询及发布；附件登记与读取。接口命名待实现时契约评审。
- 数据：新增规范化媒体引用、结论及版本、证据关联；暂不强制迁移两套历史消息存储。
- 监测：上传、处理、模型延迟、错误率、用量、成本、降级原因；日志避免媒体正文和敏感临时凭证。

## 9. 交付规划

按1名前端+1名后端、测试参与估算5—7周；模型采购和移动宿主配合另计。

| 阶段 | 时间 | 交付门槛 |
| --- | --- | --- |
| 0 基础核验 | 3—4天 | 权限及图片复现、统一入口、模型媒体契约验证、评测集 |
| 1 反馈历史 | 1—1.5周 | 统一记录、分页、搜索、日期筛选、结论发布；超20反馈/100消息完整读取 |
| 2 图片 | 1—1.5周 | 首轮/续轮/纯图/重建通过；私有资源可读与历史复核 |
| 3 原生语音 | 1.5—2周 | 录音试听、原生理解、转写纠正、图音组合、跨端授权 |
| 4 灰度 | 约1周 | 真实网关/OSS/模型验收，按项目开关，成本监测及回滚 |

## 10. 验收及开放问题

必须覆盖：跨客户会话/附件/搜索隔离；图片首轮续轮重建；媒体读取失败明确提示；长历史；中文组合筛选及时区边界；录音拒权、取消、后台、重试；幂等；转写纠正；结论版本和待验收；新消息已读边界。

上线前确定：模型供应商和部署区域、原生音频能力、媒体保留周期与删除策略、费用上限、中文/方言覆盖、结论发布权限、移动宿主支持范围。未确认项不写成既定决策。

设计原则：证据实际进入模型、历史完整可复核、正式结论可追溯，比单纯增加输入按钮更重要。

## 11. 产品定位修订：外部系统集成的双使命（本版本优先约束）

本能力不是独立客户服务工作台。它由外部业务系统以iframe/WebView等方式集成，宿主提供入口、用户身份与当前业务上下文。此前“独立侧栏工作空间”的设计不再采用，本文前述页面入口和布局建议以本节为准。

### 使命一：产品答疑与反馈建卡

用户在原业务流程中打开客服 → 基于当前产品代码仓库及文档答疑，支持文字、图片、原生音频及组合输入 → 有可靠答案时引用来源解答，不强制建卡 → 无法解答时继续澄清并区分Bug和需求；不确定时先问原有行为、期望能力及使用场景，不强行分类 → Agent结合仓库事实和证据自主判断类型 → 按类型收集 → 客户核对与明确确认 → 创建内部系统反馈卡片，并关联原咨询、媒体和结构化信息。

Bug核心字段：发生位置、实际现象、期望结果；辅助收集复现步骤、环境/版本、影响范围及发生频率。未知辅助字段允许显式待核实，不能自动编造。

需求核心字段：目标用户、模块、需求描述、使用场景、期望结果、业务目标与痛点；补充当前流程、替代方案、影响/频率、预期收益及约束。不要求用户提供故障复现步骤。需求收集完成不代表受理、合理性判断、优先级或排期承诺。

收集可跨多轮，模型依据客户原话与媒体建议预填；表单是可核对结果，不应要求用户重复填写已经提供的信息。原型用显式示例预填展示该能力，不声称真实模型已实现。编辑后撤销确认，最终确认才能建卡。重试、补充和继续澄清均不能重复建卡。

### 使命二：反馈卡片全生命周期与沟通

客户可从同一集成入口查看本人反馈，搜索问题或沟通内容、按时间筛选，查看：

1. 客户确认的原始信息与附件；
2. 卡片客户可见流转事件：提交、受理、评估/复现、实现/修复、交付、待验收、解决，及暂不采纳、请求补充等适用分支；
3. 原客服咨询、内部人员回复、客户后续补充组成的连续沟通记录；
4. 处理结论、依据、适用版本、交付与验收结果。

不暴露内部私密讨论、内部人员权限信息及不适合客户展示的任务细节。外部宿主仅显示本用户未读更新；内部人员从内部系统经同一反馈渠道回复客户，客户在原卡片继续补充，不创建新问题。状态事件由内部正式流程产生，不能由客户端任意伪造。

### 集成交互边界

宿主背景只用于解释集成关系，不属于SDK功能；SDK无独立组织、项目管理、客户工作空间。桌面默认侧边浮层，宿主可提供宽面板；移动端全屏。关闭/重新打开不丢当前咨询，默认以智能客服为首入口；我的反馈覆盖独立处理追踪。内部卡片创建成功后给出编号与进展入口，不把“已提交”写成“已受理”。

### 修订验收

- 普通产品知识问答可完成且不建卡，并能查看仓库来源。
- 未解决时由Agent自主分析Bug或需求；不确定时追问具体事实，不要求客户分类。
- 两类收集字段不同，缺失时阻止建卡，编辑后重新确认。
- 确认后卡片仅创建一次，原始咨询与媒体可追溯。
- 全生命周期包含未受理、评估、修复、待验收、解决和不采纳等客户可见分支。
- 内部回复通过原反馈渠道送达；客户可在任意阶段补充，包括解决/不采纳后请求复核；新增补充不会静默改变正式结论或状态。


## 12. 分类责任修订（优先于前述交互描述）

Bug或功能需求的判别属于智能客服Agent的分析职责，不向用户展示分类选择、类型确认或手动切换按钮。Agent综合当前产品代码仓库与文档、用户原话、图片和语音证据判断，再自主采用对应收集协议；不能只用关键词或只看“希望”等措辞决定类型。

信息不足时询问发生位置、具体操作、实际结果、原有行为、期望结果等事实，不能问“这是Bug还是新增功能”。“没有权限”也可能是正常权限机制，应先按仓库知识答疑或检查，不能直接认定代码缺陷。已有能力异常与新增能力诉求并存时，分别整理关联事项，由Agent给出处理结构，而非让客户二选一。

用户只负责补充及纠正事实、核对草稿、确认提交。用户纠正现象或期望后，Agent重新分析类型并调整字段，保留已收集的事实，更新草稿并撤销旧确认。结构化完整性规则由服务端校验，建卡仍需用户明确确认。

原型通过本地规则模拟Agent分流，只验证交互；正式实现必须使用具备仓库上下文的Agent语义分析，不将原型关键词分支移植为生产分类器。验收覆盖：自主Bug收集、自主需求收集、事实不足继续追问、正常权限问题不误判缺陷、混合诉求、用户更正后重判及重新确认；全流程无用户分类选择。
