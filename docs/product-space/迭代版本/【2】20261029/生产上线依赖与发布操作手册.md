# 【2】生产上线依赖与发布操作手册

适用版本：20261029 迭代当前工程实现。核对日期：2026-10-30。面向研发、运维及实际接入方。

本文给出从依赖准备到发布、验收、回滚的操作路径，不代表已执行生产发布。命令中的域名、项目、版本、服务器和密钥必须替换为本次发布的真实值；不直接照搬模板中的示例数据库、项目或账号。全部公开代码与产物来自 Arckit，不隐式读取相邻 arckit-ops 仓库。

## 1. 上线范围与实际边界

本次交付包含：新版 SDK 智能客服和我的反馈、独立事实反馈表单、图片与语音转文字输入、咨询历史分页与草稿恢复、真实文档依据、客户确认建卡、反馈沟通/流转/正式结论/验收与复核。配套服务为共享 Workshop API，处理人员使用 Feedback Console；Todo 是 SDK 的一个宿主。

以下事项不能按“配上环境变量就可用”交付：

- FAQ、独立文档、公共知识来源的导入适配器尚未实现。当前只支持真实仓库索引；README/Markdown 可随仓库同步供引用。不支持的知识来源明确失败，不得对外宣称已导入。
- 语音入口使用浏览器 SpeechRecognition/webkitSpeechRecognition；不具备跨浏览器统一供应商转写。目标浏览器不支持时提示改用文字。不录音上传，不自动发送转写结果。
- Todo 当前宿主代码仍为 API Key 模式，项目 ID 固定为 45；改为其他项目或 Session 模式需要修改宿主代码，不能只调整配置。
- 完成构建、单元测试不等于真实模型、OSS、网关或生产处理团队已经联调成功。

发布前明确选择“基础反馈上线”或“含智能答疑上线”。基础反馈可不启用 OpenHands，但必须明确告知 AI 暂不可用，不能产生虚假回答、虚假建卡或虚假转人工成功。独立反馈不依赖 AI，但仍依赖真实身份、API、数据库；附图还依赖 OSS。

## 2. 逐功能上线依赖

| 功能 | 必需依赖与准备动作 | 缺失时的表现/发布判断 |
| --- | --- | --- |

| 客户身份与隔离 | 网关鉴权、Workshop 项目和有效成员、稳定 custom_user_id；推荐宿主后端换取短期 Session | 身份无效友好提示，不可读写；阻断业务发布 |
| 智能答疑与多轮澄清 | OpenHands 健康、总开关、项目 Agent 配置、可用模型 Key/模型/地址、真实项目仓库全部同步、共同工作区及网络可达 | 不得输出伪造答案；含 AI 的上线验收必须失败，基础反馈可单独验收 |
| 产品文档依据 | 同步仓库中真实 Markdown/README、模型返回引用、服务端成功校验路径与行号 | 无有效依据时不展示引用；不能保证每条答案必有来源 |
| 图片上传与预览 | OSS 私有 Bucket、服务端 AK/STS Role/策略、Bucket CORS、临时访问、上传大小/MIME 约束 | 图片上传/读取失败明确提示；文字反馈可独立使用 |
| 客服理解图片 | 上述图片能力 + AGENT_VISION_ENABLED=true + 实际模型支持图片 + 模型能访问签名 URL | 不得把已上传等同于已理解；不支持时明确失败 |
| 语音输入 | 支持识别的浏览器、HTTPS、用户麦克风许可、iframe allow 与宿主 Permissions-Policy、识别服务网络可达 | 不支持/拒绝权限时保留文字草稿并提示；不会上传音频 |

| 草稿恢复 | 浏览器允许本地存储、同一项目/客户/咨询作用域 | 清理站点数据/禁用存储不能保证恢复；未上传文件需重新选择；恢复后重新确认 |
| 团队回复、正式结论、验收/复核 | Console 新版本、内部 JWT 登录、项目成员权限、反馈受理人员、真实结论发布流程 | SDK 页面存在不等于有人处理；必须完成一次真实双向闭环 |

## 4. 环境配置与基础设施

### 4.1 Workshop 与网关

以 `services/workshop-api/deploy/prod/env.workshop.production.example` 为字段模板，在受控部署环境准备 `.env.workshop.production`，不要提交真实文件。脚本会 source 该文件，值须符合 shell 赋值格式；含特殊字符的值正确引用。

| 配置组 | 必填/按需配置 |
| --- | --- |
| 服务/数据库 | ENV=production、SERVICE_NAME=workshop、HOST、PORT、DB_HOST/PORT/USER/PASSWORD/NAME/SSLMODE；生产按数据库证书配置 TLS，不照搬模板 disable；DB_AUTO_MIGRATE=false |
| 部署 | PROD_SERVER_HOST、PROD_SERVER_SSH_USER/PORT/KEY_PATH、SERVER_DEPLOY_DIR、IMAGE_NAME、唯一 IMAGE_TAG、DEPLOY_BACKUP_DIR |
| Session | FEEDBACK_SESSION_SIGNING_KEY、FEEDBACK_GATEWAY_SHARED_SECRET；Workshop 与网关各自同名配置一致，两项密钥彼此不同且至少32字节 |
| 跨域 | CORS_ALLOW_ORIGINS 列出实际 SDK/宿主/Console origin；网关也要允许 Authorization、Content-Type 和 OPTIONS，避免重复冲突 CORS 头 |
| OSS | OSS_ACCESS_KEY_ID/SECRET、OSS_BUCKET_NAME、OSS_REGION、OSS_RAM_ROLE_ARN、OSS_ROOT_PATH；权限限制到实际上传范围 |
| Console 自反馈 | 如使用该能力配置 FEEDBACK_CONSOLE_PROJECT_ID，与真实自反馈项目匹配 |
| 邮件（选配） | FEEDBACK_EMAIL_NOTIFICATIONS_ENABLED、FEEDBACK_NOTIFICATION_EMAIL_URL、FEEDBACK_NOTIFICATION_SHARED_SECRET、FEEDBACK_CONSOLE_BASE_URL，密钥与通知网关匹配 |

网关必须已支持 `/workshop/v2/feedback/*` scoped token、`/workshop/v2/apikey/*` 和 `/workshop/v2/user/*`，并清除外部伪造身份头后注入可信身份。业务容器不要绕过网关对公网直接暴露可信头接口。网关工程不在本仓库；由对应负责人提供版本及验收记录。

### 4.2 智能答疑

在基础服务之外准备：

- `OPENHANDS_ENABLED` 显式设为 false，直到 Agent 服务、模型和项目知识都验收通过再设 true，避免依赖代码默认值。
- `OPENHANDS_IMAGE` 固定 digest；`OH_SESSION_API_KEYS_0`、`OH_SECRET_KEY`、`OPENHANDS_CONFIG_ENCRYPTION_KEY` 使用稳定且不同的至少32字符密钥。加密 Key 变更会影响既有项目模型密钥解密，不能随重部署重生成。
- `LLM_API_KEY/LLM_BASE_URL/LLM_MODEL` 为服务级兜底；项目 owner/admin 可在 Console 保存项目模型配置，项目配置优先。至少一套真实模型凭据有效。
- `CUSTOMER_REPOS_PATH=/opt/todo/customer-repos` 为宿主机目录示例；Workshop 读写，OpenHands 只读，二者容器中均为 `/workspace/customer-repos`；`OH_REPO_ROOT` 和 `OH_WORKSPACE_DIR` 显式使用此路径。
- 多仓库使用 `.agent-workspaces/<project>/<digest>/repo-<id>` 受控入口；所有配置仓库必须真实同步就绪，不能只挂一个仓库或回退共享根目录。相同绝对路径和符号链接目标在 Agent 执行环境也必须可读。
- 当前 Compose 给 Agent 挂载整个仓库根目录。应用层项目路径约束不等于进程级租户沙箱；有强隔离要求时必须额外配置每项目容器/文件系统隔离后才能承诺强隔离。
- 私有仓库 clone/pull 的凭据、Git 服务连通性、模型服务出网、模型到 OSS 的访问均需单独验证。

在服务器的实际 `SERVER_DEPLOY_DIR/deploy/prod` 下执行（以下以 /opt/todo 为例）：

```bash
cd /opt/todo/deploy/prod
bash ./openhands-control.sh preflight
bash ./openhands-control.sh start
bash ./openhands-control.sh status
```

控制脚本要求至少1536MiB可用内存和2048MiB swap（默认值），并检查 digest、密钥和目录。不要只为绕过检查降低门槛；按实际容量调整资源。普通 API 发布不会自动启动/重启 OpenHands，需显式执行上述步骤。

项目配置与就绪验证通过 Console 或真实 JWT 调用现有接口：`/workshop/v2/user/projects/:id/openhands-config`（GET/PUT）、`openhands-health`、`knowledge/sources`、`knowledge/sources/:sourceId/reindex`、`knowledge/workspace`、`knowledge/retrieve-test`。重建索引后检查真实结果、分支、失败原因；不能仅凭 HTTP 已受理即认定同步完成。

### 4.3 SDK、宿主和静态站点

- SDK 复制 `apps/feedback-sdk-web/env.production.template` 为受控 `.env.production`；配置 `VITE_GATEWAY_URL`、`VITE_SDK_PARENT_ORIGINS`（精确 origin，不带路径）。跨域父页面必须构建进白名单，不能靠首次 configure 自行授权。
- 不在 Vite 变量、URL、持久化存储或日志中写入 Session token。VITE_* 是公开构建内容；不要当作秘密存储。
- HTTPS、证书、DNS、CDN/OSS 域名先就绪；入口/channel 不长期缓存，版本化资源可长期缓存。SPA 别名/回源路径要真实可达，禁止登录页或 HTML 错当 JS 返回。
- 宿主 CSP 允许 SDK frame，SDK 响应允许实际宿主嵌入；host 的 connect-src 允许其会话接口。图片直传的 Bucket CORS 允许 SDK origin 的 POST，读取方式按真实网络请求放行。
- 语音需 iframe `allow="microphone"`，宿主 `Permissions-Policy` 允许 SDK origin，且 SDK 响应不再禁止麦克风；实际浏览器识别网络也需可达。

## 5. 宿主接入操作

推荐 Session 路径：宿主后端持有 API Key，从已登录业务用户生成稳定 custom_user_id，不能直接相信浏览器提交的其他用户 ID。调用 `POST /workshop/v2/apikey/feedback-sessions`，body 为 `project_id`、`custom_user_id`，只向浏览器返回15分钟短期 token。

iframe 收到 `feedback-sdk:ready` 后注入以下配置，再发送 open：

```js
// token 来自宿主后端；sdkOrigin 为实际 SDK origin。
iframe.contentWindow.postMessage({
  source: 'feedback-sdk-host', type: 'feedback-sdk:configure',
  config: {
    feedbackV2Enabled: true,
    feedbackV2AuthMode: 'session',
    feedbackV2NotificationsEnabled: true,
    feedbackSessionToken: token,
    gatewayUrl: 'https://api.example.com',
  },
}, sdkOrigin)
iframe.contentWindow.postMessage({
  source: 'feedback-sdk-host', type: 'feedback-sdk:open', mode: 'submit',
}, sdkOrigin)
```

父页面监听消息时必须同时校验 `event.origin === sdkOrigin` 和 `event.source === iframe.contentWindow`。处理 `feedback-sdk:refresh-session`：重新向宿主后端获取当前用户 token 并 configure，不复用过期 token；处理 `feedback-sdk:close` 隐藏/销毁 iframe。登出/换账号清理原 iframe 并注入新用户身份。不要直接从跨域父页面调用 iframe 内 window.FeedbackSDK 或读取 SDK DOM。

现有宿主差异：

| 宿主 | 需要的发布动作 |
| --- | --- |
| Feedback Console | 配置 `VITE_FEEDBACK_SDK_URL` 指向已发布 canary/stable alias，`VITE_FEEDBACK_V2_PROJECT_IDS` 加入目标项目；保留原 V1 `VITE_API_URL`，按需配 `VITE_WORKSHOP_V2_API_URL`；重新构建发布。JWT 交换 token 仍要求正确成员权限。 |
| Todo Web | 配置 `VITE_FEEDBACK_SDK_URL`（默认同源 `/sdk/index.html?embed=web`）、`VITE_FEEDBACK_API_KEY`、`VITE_GATEWAY_URL`；当前代码项目45且 API Key 模式。发布 SDK 到该域名对应 Bucket 或指定跨域地址并配置白名单，然后重新构建发布 Todo。 |
| 其他 Web/WebView | 自行实现上述后端签发、ready/configure/open/refresh/close 和身份变更；不能只嵌一个 URL 就视为完成接入。 |

API Key 模式可运行，但浏览器中的 Key 可被提取，不能达到 Session 模式的身份保护效果。上线前接入方明确选择风险、使用可撤销专用 Key、配置限流和监控；安全目标要求服务端身份绑定时必须完成 Session 接入开发。

## 6. 构建、迁移与发布顺序

### 6.1 候选版本验证

在固定 release commit 的仓库根目录执行；构建 `.env.production` 按上一节先准备：

```bash
npm ci
npm test --workspace @arckit/feedback-sdk-web
npm run test:release --workspace @arckit/feedback-sdk-web
npm run build:check --workspace @arckit/feedback-sdk-web
npm test --workspace @arckit/feedback-console
npm run build:check --workspace @arckit/feedback-console
npm test --workspace @arckit/todo-web
npm run build --workspace @arckit/todo-web
```

后端在 `services/workshop-api` 中执行：

```bash
# 仅使用一次性测试数据库，绝不能指向生产库。
WORKSHOP_TEST_POSTGRES_DSN='<temporary-test-postgres-dsn>' go test -race ./... -count=1
```

未提供测试 DSN 时部分事务/权限测试跳过，不视为完整验证。Todo 严格类型检查存在已记录的既有错误，当前 Vite build 通过不能替代 tsc；本次发布记录中单独注明检查结果及处置，不声称全仓类型检查通过。

### 6.2 网关、API 与数据库

1. 先发布兼容 V1 的 scoped-token 网关，验证路由、签发、CORS 与伪造头防护。备份原网关版本及配置。
2. 核对生产目标数据库、权限、空间、备份策略与回滚窗口。正常 API 启动不做隐式迁移。
3. 从 `services/workshop-api` 执行：

```bash
# .env.workshop.production 已填好；建议使用唯一 tag。
DEPLOY_IMAGE_TAG_OVERRIDE=feedback-20261030-rc1 ./deploy.sh prod
```

当前脚本实际流程：构建并上传候选镜像 → 保存上一镜像回滚标签 → 候选镜像执行 pg_dump custom-format 备份并用 pg_restore --list 校验 → 候选镜像 `./todo migrate` → 准备仓库目录 → 重建 API 容器 → 健康检查，切换失败尝试恢复上一镜像。备份或迁移失败不得继续切换。

**不要按旧 runbook 仅执行 20260715 单个 SQL 就发布**；本迭代还依赖 SupportTurn、结论、客户响应等模型/迁移。以当前候选镜像 `./todo migrate` 为权威入口。若采用其他发布平台，也必须把备份、该迁移命令、校验、健康切换落实为独立步骤，不能只 docker compose up。

4. 检查部署日志中备份位置、迁移成功、镜像及健康检查结果。数据库备份列表可读不等于恢复演练成功；正式发布前应在隔离库完成恢复演练。
5. 启动并验收 OpenHands，补齐项目配置/仓库/模型后，将 `OPENHANDS_ENABLED=true` 通过 API 容器重建生效。只改 env 文件不改变运行中的进程。
6. 检查 `GET /workshop/v2/public/health`，并用真实身份执行一笔读写；健康检查不能替代 AI 与业务验收。

### 6.3 SDK 不可变产物与灰度

在 `apps/feedback-sdk-web` 执行，版本仅为示例；`<private-oss-env>` 是显式提供的发布配置，不是前端 .env.production：

```bash
npm run build:release -- 2.0.0-canary.20261030
python3 scripts/sdk_release.py publish \
  --version 2.0.0-canary.20261030 --dist-dir dist \
  --env-file '<private-oss-env>' --compatible-contracts v1,v2 \
  --source-commit '<reviewed-commit>'
python3 scripts/sdk_release.py promote \
  --version 2.0.0-canary.20261030 --channel canary \
  --env-file '<private-oss-env>' --alias sdk-v2-canary:v2 \
  --confirm-promote canary:2.0.0-canary.20261030
```

发布配置文件必须包含 `OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`、`OSS_ENDPOINT`、`OSS_BUCKET_NAME`，可选 `OSS_CUSTOM_DOMAIN`；这是上传凭据，不能打包进 dist。发布前用受控文件权限保存（例如 chmod 600），并先核对 Bucket 所属环境。可在 SDK 目录创建独立 Python 环境后再执行上述脚本：

```bash
python3 -m venv /tmp/arckit-sdk-release-venv
source /tmp/arckit-sdk-release-venv/bin/activate
python3 -m pip install oss2 python-dotenv
```

生产团队可替换为自身受控且固定依赖版本的发布环境。同一个版本内容不同会拒绝上传。先验收 `/sdk-v2-canary/index.html?embed=web`，不要覆盖旧稳定入口测试。若 Todo 和 Console 使用不同 Bucket，向各 Bucket 发布同一产物，并分别保留旧 channel JSON；跨域宿主白名单必须涵盖所有目标 origin。

验收通过后，把同一产物 promote 到 stable，并逐个列明实际要切换的 alias：

```bash
python3 scripts/sdk_release.py promote \
  --version 2.0.0-canary.20261030 --channel stable \
  --env-file '<private-oss-env>' --alias sdk-v2:v2 \
  --confirm-promote stable:2.0.0-canary.20261030
```

此处只切 `/sdk-v2`。Todo 默认 `/sdk` 不会因此更新；若要替换 `/sdk`，必须另行验证 v1 宿主兼容后显式 `--alias sdk:v1`。一个 channel 的 alias 应一次列全需继续维护的入口，避免后续 promote 遗漏通道映射。生产不运行 cleanup-root 或删除旧 release。

### 6.4 Console 与 Todo 发布

先发布 SDK 再发布引用它的宿主。前端环境变量为构建时配置，修改服务器文件不自动改变线上包。

- Console：根目录 `npm run deploy:oss --workspace @arckit/feedback-console`，使用其 `script/README.md` 所述发布环境。先确认目标为 Console 前缀，不覆盖 SDK/其他产品。
- Todo：在 `apps/todo-web` 目录准备上传使用的受控 `.env`（OSS_ACCESS_KEY_ID/SECRET、OSS_ENDPOINT、OSS_BUCKET_NAME 等，详见脚本说明），执行 `npm run build` 后 `bash script/deploy-oss.sh`，确认实际根入口/前缀和对应 Bucket；不要照搬旧文档中的 frontend 路径。上传环境同样需要 oss2 和 python-dotenv。
- 非 OSS 环境：上传各 workspace 的 dist 到各自独立站点/前缀；资源先上传、HTML 最后切换，保留上一版产物；验证 SPA 回退和静态 MIME。
- 检查入口与 channel 的 Cache-Control/CDN 回源；浏览器实际收到的 ready 中 sdk_version/build_id 与本次发布一致。不要仅凭本地 dist 判断上线生效。

## 7. 生产灰度验收（逐项留证据）

使用独立测试项目、客户 A/B 与真实处理账号，避免操作真实客户反馈。每项记录请求结果、反馈/咨询 ID、截图或日志关联 ID；不记录 token/密钥。

| 验收项 | 操作与通过标准 |
| --- | --- |
| 入口与视觉 | 从真实宿主打开，检查窄/宽/390px、头部图标、历史弹层、关闭重开；无裁切/横向溢出，版本正确 |
| 身份 | A 创建咨询与反馈，切换 B 不残留 A；B 无法通过修改 ID 读取 A 的记录与图片；Session 过期能刷新一次，退出后不能继续调用 |
| AI 真实答疑 | 用仓库中可核验的问题测试，引用路径/行号与真实文档一致；多仓库各选一题，确认覆盖的 branch/commit |
| AI 异常 | 在隔离灰度配置中使用不可达模型/关闭开关，页面友好提示，无伪造答案、交接或成功反馈；直接反馈仍可填写 |
| 事实提交与幂等 | 填写事实/勾选确认创建成功，重复相同请求只有一张卡；改变事实不能复用同回执静默覆盖，未确认不提交 |
| 草稿与历史 | 编辑文字/字段后切咨询、关闭重开，恢复同身份草稿且确认重置；历史多页/消息多页无丢失重复，未上传文件提示重选 |
| 图片 | 真实设备上传/预览/刷新读取成功；A/B 图片隔离；过期签名可重新取；启用视觉时实际能回答图片内容，禁用时不谎称看懂 |
| 语音 | 目标浏览器允许麦克风后转入可编辑文本，未点发送前无消息；取消保留原草稿，拒绝/不支持有真实提示 |
| 完整处理 | Console 看到原始事实快照和图片→团队回复→客户补充→真实任务流转→发布正式结论→客户验收/复核，原卡片不重复创建 |
| 刷新与通知 | 客户与团队双向看到新消息，未读更新及已读正确，后台/切回后刷新；开启邮件时验证 outbox 和实际收件 |
| 故障与可观测 | OSS/模型/网关超时有友好话术，输入不丢；服务日志可关联问题，无密钥与客户原始敏感内容泄露 |

先单项目/内部账号验收，再扩大配置范围。观察窗口由发布负责人明确记录；持续观察5xx/401/403、AI 超时、OSS 上传失败、重复建卡、通知积压、容器重启/OOM、磁盘/DB 连接。发现串号、错误仓库来源、数据写入失败或虚假成功立即停止扩大并回退。

## 8. 回滚与故障定位

### 8.1 回滚顺序

1. 先把宿主 URL/项目灰度开关恢复到已验证旧入口并重新构建发布，阻止新增问题流量；保留真实客户已写入数据。
2. SDK 使用同一 promote 命令将对应 channel 指向之前已发布的版本，列全本次维护的 alias。分别回退各 Bucket，验证 ready 版本；不删除 release 资源。
3. API 发布切换失败脚本会尝试恢复上一镜像。手动回退时从已记录镜像/digest 恢复，使用相同 env/volume 重建并检查健康与实际读写；不要盲目依赖可能已被后续部署覆盖的 rollback 标签。
4. AI 问题可先 `OPENHANDS_ENABLED=false` 并重建 API 保留基础反馈；必要时停止 OpenHands，但这不修复网关/DB/OSS。
5. 应用回退不自动回退数据库。优先保留兼容新增表/列；任何 down SQL 或备份恢复由 DBA 评估，先停止写入并明确迁移后数据保留方案，禁止在线直接清库或恢复覆盖新反馈。

### 8.2 定位表

| 现象 | 优先检查 |
| --- | --- |
| 页面正常但仍是旧样式 | 实际 SDK URL、Bucket、alias/channel、CDN/浏览器缓存、ready 版本；确认只更新 sdk-v2 却仍打开 sdk 的情况 |
| iframe 一直加载/配置不生效 | ready 消息、event.source/origin、构建白名单、CSP/frame-ancestors、脚本 MIME、宿主15秒加载超时 |
| Session 401/403 | 网关 scoped-token 版本与双共享密钥、时钟、项目成员资格、token 绑定客户、宿主刷新逻辑 |
| AI 不可用 | 总开关、项目 Agent health/config、解密密钥是否变化、模型 Key/额度/地址、工作区每个仓库状态、容器出网/OOM |
| 来源与项目不符 | 立即停用 AI，核查 repo URL/branch/source ID、容器目录/符号链接、项目隔离；不能通过放宽共享目录回退解决 |
| 图片上传/显示失败 | 策略签名、Bucket region/CORS、STS Role、对象前缀/归属、临时签名过期、模型访问 OSS 网络 |
| 反馈提交失败 | 身份/DB schema/迁移日志/权限、client_request_id payload 一致性；不得改成前端假成功 |
| 语音按钮不可用 | 浏览器 API 支持、HTTPS、系统/页面权限、iframe allow 与 Permissions-Policy、识别网络；不是先去配音频模型 |
| 团队进展不更新 | Console 版本与 V2 项目开关、真实处理账号权限、轮询/WS 代理、正式结论是否已发布；任务完成不等于客户已验收 |
