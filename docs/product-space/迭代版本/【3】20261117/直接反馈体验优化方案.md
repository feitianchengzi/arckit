# 直接反馈体验优化：问题反馈降门槛与需求提交通道

> Proposed / 2026-11-17。本文沉淀「仍未解决 / 直接反馈」入口的体验诊断、优化方案与优先级。设计稿为模拟交互，不连接后端或真实模型；工程落地后以实际验证为准。

## 1. 背景与问题

「仍未解决 / 直接反馈」是智能客服的逃生通道：客服未解决问题、或客户不想继续对话时，可跳过 Agent 直接填写事实创建反馈卡片。当前实现为三个并列结构化输入框：

| 字段 | 当前 label | 来源 |
| --- | --- | --- |
| position | 问题位置 | PRD F-01 Agent 结构化三字段 |
| phenomenon | 实际现象 | 同上 |
| expect | 期望结果 | 同上 |

评审反馈集中在两点：

1. **用户不理解这三个框**。字段名是给结构化分析用的内部术语，不是用户语言；用户不知道「问题位置」指页面 URL 还是功能模块。
2. **当前只实现了问题反馈，需求没有入口**。用户想提功能建议时不知道从哪里提交，直接反馈通道会把一切归为「其他」。

## 2. 诊断（代码与设计稿核对结论）

### 2.1 实现丢失了设计稿已有的引导

设计稿 `【2】20261029/设计稿/feedback-web.html` 的 `manualFields` 本就带引导语：

- 问题位置 →「在哪个页面或操作中遇到问题？」
- 实际现象 →「实际发生了什么？」
- 期望结果 →「希望怎样处理？」

工程实现 `apps/feedback-sdk-web/src/components/sdk/ManualFeedbackForm.tsx` 只渲染 label，placeholder 全部丢失。这是实现对设计稿的回归。

### 2.2 三框全必填，没有降级路径

`ManualFeedbackForm.tsx` 要求三框 trim 后全部非空才能提交。后端与核对表单（`ClarificationReview`）已有 `unknown_fields`「暂时无法提供，保留为待确认」机制，直接反馈通道没有接入：用户被强迫为每个框编造内容。

### 2.3 与对话上下文脱节（最严重的断点）

用户点「仍未解决」的前提是刚与客服对话过，会话中 Agent 可能已产出结构化草稿（`structured`）。但当前实现：

- `openManual()` 打开的是**空白三框**；
- 已预填的 `ClarificationReview` 因 `!manualOpen` 条件被互斥隐藏。

用户刚说过的内容被丢弃，需要重打一遍。直接反馈表单与对话上下文完全脱节。

### 2.4 需求分类被硬编码丢弃

`ManualFeedbackForm.tsx` 提交时写死 `request_type: 'other'`，说明文案也声明「不会自动判定为故障或需求」。需求从这条通道进入即丢失分类信息。

### 2.5 需求路径其实已存在于对话流，缺的是感知

| 环节 | 现状 |
| --- | --- |
| 对话入口 | 欢迎语建议含「我想提出一个功能建议」 |
| Agent 分类 | 后端自主判 `bug/feature/question/other`，明确不询问客户类型 |
| 需求字段组 | `structured.ts` 已定义 featureCoreFields / featureContextFields，核对表单按类型切换渲染 |
| 直接反馈通道 | 硬编码 `other`，需求进来丢分类 |
| 我的反馈列表 | `FeedbackItem` 无类型字段，设计稿的 Bug/需求徽标未实现 |
| 管理端 | `feedback-console` 未消费 `request_type`，处理团队看不到分类 |

## 3. 产品约束（不可违反的既定决策）

1. **类型由 Agent 自主分析，不询问客户**。后端 prompt 明确要求：「request_type 由你作为 Agent 自主分析……不得要求客户选择、确认或切换类型，不问『这是Bug还是功能需求』」（`agent_feature_clarification.go`）。对话收集流程不得出现类型选择器。
2. **AI 异常时直接反馈仍可填写**。发布手册要求模型不可用不阻断真实反馈，手填表单必须保留为降级模式。
3. **收集完成不等于受理**。所有建卡须客户显式确认；受理、优先级、排期由内部团队决定。
4. **直接反馈通道的定位是「客户自述事实 · 团队待分析」**（设计稿原话），与对话流程中「Agent 分析整理」并存。类型选择器是否允许出现在该通道，见 §6 待拍板项。

## 4. 优化方案（按优先级）

### P0 文案与结构修复（纯前端，半天）

1. **恢复设计稿 placeholder，label 换用户语言**：

   | 现状 | 优化后 | placeholder 示例 |
   | --- | --- | --- |
   | 问题位置 | 在哪里遇到的？ | 例如：项目列表页，点导出按钮时 |
   | 实际现象 | 你看到了什么？ | 例如：页面提示 403，下载失败 |
   | 期望结果 | 你本来想做什么？ | 例如：正常导出月度报表 |

2. **必填放宽**：「你看到了什么」必填；另两框提供「不确定，由团队稍后补充」勾选，写入 `unknown_fields`（机制现成）。
3. **修复上下文断点**：对话已产出结构化草稿时，点「仍未解决」默认进入**已预填、可编辑的核对表单**；空白手填表单降级为「跳过分析，直接填写」的次级入口。无对话上下文时直接进手填表单。
4. **说明文案改写**：「不会自动判定为故障或需求」是内部视角话术，改为用户语言，例如「描述你遇到的情况即可，处理团队会跟进；不确定的内容可以留给我们补充」。

### P1 需求通道补齐（1–2 天）

1. **我的反馈列表/详情加类型徽标**：`structured.request_type` 已随提交写入 metadata，UI 消费即可；设计稿的 Bug / 需求 / 一般反馈徽标样式现成。
2. **列表加类型筛选**：与状态、日期筛选并列。
3. **直接反馈入口文案明确承接需求**：「功能建议、产品需求也在这里提交」；欢迎语建议条已有对应入口，保持一致。
4. **管理端消费 `request_type`**：反馈列表加类型徽标与筛选，处理团队可分流；否则客户端分类无人使用。

### P2 单框自然语言 + 机器结构化（核心体验升级）

直接反馈主输入改为**一个大文本框**：「发生了什么？像跟同事口头描述一样写就行」。两条实现路线：

- **B1 轻量**：一段话原样提交，结构化留给处理团队或后续对话补齐。零新接口，但卡片丢失结构化字段，与后端澄清流程脱节。
- **B2 推荐**：单框内容作为客户消息进入会话，触发既有 Agent 分析链路，弹出**预填好的核对表单**（`ClarificationReview`）确认后建卡。不新增接口；`request_type` 由 Agent 判定，符合 §3 约束 1，需求也能正确分类；与主路径体验统一。模型不可用时降级为 P0 手填表单（满足 §3 约束 2）。

## 5. 设计稿呈现

[设计稿/feedback-direct.html](设计稿/feedback-direct.html) 以三档方案切换对比呈现：

- **A 当前版本**：三术语框全必填、与对话脱节、无类型徽标（现状还原）。
- **B P0 优化**：预填核对优先、用户语言手填表单、不确定降级、类型徽标。
- **C P2 单框 + 结构化**：单框自然语言 → 机器整理 → 按类型预填核对（含需求字段组）→ 建卡。

评审路径与边界见 [设计稿/README.md](设计稿/README.md)。

## 6. 待拍板项

1. P2 采用 B1 还是 B2？（本文推荐 B2）
2. 直接反馈通道是否允许客户**自报**「这是需求」（只影响字段组与预标注，标注「客户自报 · 待团队复核」），还是坚持类型只能由分析得出？该通道本身绕过 Agent，与 §3 约束 1 的边界需要明确。
3. 管理端（feedback-console）类型分流是否本期一起做？

## 7. 落地拆分建议

| 优先级 | 改动 | 文件范围 | 依赖 |
| --- | --- | --- | --- |
| P0 | 文案、placeholder、必填放宽、预填衔接 | `ManualFeedbackForm.tsx`、`SDKSupportPage.tsx`、`AgentChatPanel.tsx` | 无 |

## 8. 验收要点

- 从未对话直接打开：手填表单可用，仅一个必填框，「不确定」可勾选。
- 从对话点「仍未解决」：看到的是已预填核对内容，而非空白表单；可编辑、可跳过分析改为直填。
- 模型不可用：直接反馈手填路径不被阻断，提交成功。
- 需求场景：对话提需求 → 核对表单显示需求字段组；提交后列表显示「需求」徽标。
- 提交失败：草稿保留，不展示成功，不编造反馈编号。
- 管理端：可按类型筛选与查看（若本期纳入）。
