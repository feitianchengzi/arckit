# 平台内交互方案：基于现状链路的挤压区、卡片讨论与自动化升级

> Proposed / 2026-11-19。本文是**对现有 Web（feedback-console / todo-web）与 ArcOrbit 桌面端（runtime/arcorbit）真实链路的功能升级**，每个升级项标注现状组件与落点端；不引入与现状无关的平行逻辑。共享模型（挤压区、讨论状态、注入规则、事件契约）单点定义在 [../README.md](../README.md)。设计稿为模拟交互，不连接后端或真实模型。

## 1. 背景与问题

反馈是待办的一种渠道：反馈内容成为待办面板挤压状态的一张卡片，团队围绕卡片讨论决策，通过后进入待办，Agent 按自动化规则获取卡片、拆解任务、遇阻主动提问；卡片携带项目与仓库上下文。**沟通是待办的过程性行为，不是待办详情的组成部分**：待办默认**未开启讨论**（详情只有「开启讨论」入口，无讨论状态区域，徽标「未讨论」）；显性开启后进入独立「沟通空间」——Agent 常驻并给出初步分析、可添加平台用户（计入投票分母）、结论草案需**超过半数人类参与者赞成后显性通过**（Agent 不计入分母；单人参与者提交即通过）；通过后结论回写 `task.decision` 成为状态流转与执行上下文依据，Agent 异步生成过程摘要（不阻塞流转），讨论全文与摘要均不注入 Agent 执行工作。**未开启讨论的任务也可直接变更状态，但进入执行/验收必须弹「未经讨论决策」风险确认。**

对照现状链路（真实组件）：

```
反馈受理（console 行内动作 / 桌面 Feedback 页 + ensureFeedbackTriage）
  → 一次性流转 ConvertFeedbackToTask（feedback_task_links + Task.source_feedback_id）
  → 待办面板（todo-web TasksPage 按项目分组 / 桌面 Work 页七态 chips + 表格）
  → 卡片讨论（CommentSection / 桌面 task-comment-panel，均为 task.attachments）
  → 自动化（automation-coordinator：仅 pending ∧ 本地绑定 ∧ 项目参与 → lane 串行领取）
  → Agent 执行（buildAutomationTask 只取 content/title + ledger/Case）
  → 阻塞（attention_items.human_decision.question → attention-strip → 介入工作台）
```

差距不在「缺一套新系统」，而在**五个衔接断点**：流转没有讨论决策场；两个沟通平面割裂；面板没有挤压段；自动化状态口径与讨论结论不衔接；Agent 提问原语与卡片讨论平面互不相通。

## 2. 现状诊断（代码证据，按链路顺序）

### 2.1 流转是一次性动作，无讨论决策场

`services/workshop-api/handler/feedback_workflow.go::ConvertFeedbackToTask`：原子建 Task、写 `feedback_task_links(is_primary)`、`triage_status → accepted`、`status → converted`。Web 侧入口是 `FeedbackManagementDialog` 行内「流转为待办」+ `CreateTaskDialog`；桌面侧是 `platform-coordinator.mjs` action `feedback.to_task`（action 表 L472-583）。两端都**一步直达**，没有「值不值得做」的中间态。

### 2.2 两个割裂的沟通平面

| 平面 | Web | 桌面 | 服务端 |
| --- | --- | --- | --- |
| 反馈会话 | `FeedbackConversationPanel` 四角色会话流 | Feedback 页 `renderFeedbackConversation` | `feedback_messages` |
| 卡片评论 | 抽屉 `CommentSection`（`useTaskComments`） | 详情 `task-comment-panel` 时间线（`renderer.js:3377`） | `task.attachments`（type=text） |

互相不可见：反馈会话不显示卡片评论摘要，卡片详情不显示反馈讨论结构；两者都无「议题/结论」结构。

### 2.3 面板无挤压段

- Web：`TasksPage` 按项目分组 + 七态筛选，`ProjectDetailPage` 统计四态——反馈来源卡片与普通卡片不可区分。
- 桌面：Work 页是**七状态 chips 计数 + 单状态表格**（`renderPlatformWork`，`renderer.js:2981`），无跨状态分组；`blocked_pending_tasks`（不合格候选）只在 Automation 页与详情 guidance 出现，**Work 列表行不显示「为何不能自动执行/正在讨论」**。

### 2.4 自动化的状态口径断点（Web 默认态 vs 桌面准入）

- 服务端 `CreateTask` 默认 `state = pending_review`（`handler/task.go:121-124`）。
- 桌面 `buildPendingCandidates`（`automation-coordinator.mjs:2937`）**只认 `state === "pending"`**，且要求本地绑定 + `project_participation`；领取用 `updateTaskState(expectedState:"pending")` 乐观并发。
- 单任务手动领取 `enqueueTask`（L324，要求 pending ∧ 执行人=自己）**仅 workbench 内部调用，未暴露到 Work 详情 UI**。
- 结论：讨论通过后的卡片必须显式落 `pending` 才可能被自动领取；本方案的状态衔接（§4 P1/P2）以此为准，不改准入三条件。

### 2.5 Agent 执行上下文本就不读协作记录（注入规则的现状基线）

`buildAutomationTask`（`automation-coordinator.mjs:3333`）= `task.content ?? task.title`；评论/附件全仓无进入 `runtimeContext` 的调用；真正的语义上下文来自 Arckit ledger/Case 快照，轮间压缩在 `session-thread.mjs`（≥0.8）。**「讨论全文不注入」是既有事实而非新约束**；缺的是把「决策结论一行」显式接入 `continuationContext.original_task`（L3540）。

### 2.6 Agent 提问已有原语，但与卡片平面脱节

桌面已有完整链路：`executionOutcome` → `setAwaitingHuman(kind:"human_decision", question)`（L2544）→ `attention-strip` 条幅（`renderAttention`，`renderer.js:5666`）→ 介入工作台 `interventionComposer` 提交恢复。缺口：**提问不回写卡片、不进讨论时间线、不产生通知**（automation 事件仅静默刷新 + 单条 toast），用户必须停在 Automation 页才能感知。

### 2.7 通知与事件管道现状

服务端 `project_events` 事务内写入（`realtime_helpers.go::recordProjectEvent`）+ WS/游标回放；桌面 `arckit:automation-event`/`work-sync-event` IPC → 80ms 防抖静默刷新、`showToast` 单条 4.2s、导航徽标（`attentionNavCount` 挂 Today）。出站（给外部系统）没有机制——那是模式B 的范围。

## 3. 产品约束（不可违反的既定决策）

1. **不新增第八种任务状态**。七态弱状态机 + 反馈侧 5 套状态口径的教训；挤压区做成面板状态段/徽标，不进 `tasks.state`。
2. **讨论全文不注入 Agent 执行**——与 `buildAutomationTask` 现状一致，保持；唯一增量是结论一行进 `continuationContext`。
3. **决策权在人**：Agent 可预分析、发观点、拆草稿、提问；「标记决策结论」仅人可执行。
4. **反馈状态仍由待办状态驱动**（`syncLinkedFeedbacksFromTask` 单向回写），不反向伪造。
5. **复用既有原语，不新造平行系统**：讨论渲染复用 `CommentSection`/`task-comment-panel`（收缩为摘要）并升格为沟通空间视图；提问复用 `attention_items`+介入工作台；事件复用 `recordProjectEvent`；通知复用既有 toast/徽标与 `task_notification_preference`；自动化不改准入三条件与 lane 语义。
6. **详情与沟通空间职责分离**：待办详情 = 状态与依据（事实表 + 状态流转动作 + 讨论区）；沟通空间 = 过程行为（参与者/议题/观点/结论草案/投票/全文）。**未开启讨论的详情不显示任何讨论状态区域，只有「开启讨论」入口**；开启后详情回显摘要卡（徽标/议题/最近 1 条观点/结论一行 + `decision` 回写说明）。结论通过是沟通空间内的 action，**回写 `task.decision` 字段**；执行上下文、自动化准入、通知只读 `decision`，不读讨论流与过程摘要；详情不内嵌完整讨论时间线。
7. **讨论确认机制（多数决）**：开启讨论 = 显性动作，开启者自动入列参与者，Agent 常驻并写入初步分析；参与者为**人类用户**（Agent 常驻但不计入投票分母），参与者栏显示参与成员头像，由参与者通过**项目成员选择器**点选添加（仅列已加入本项目的成员，加人即入分母 + 站内通知），非参与者可「加入讨论」；确认流程 = 任一参与者起草结论草案（起草人自动记赞成）→ 多人需**赞成 > 参与者数/2** 后由任一参与者显性点「通过结论」，**单人参与者提交草案即通过**；通过后回写 `task.decision`、卡片离开挤压区、出拆解草稿，Agent 异步生成过程摘要（800ms 级，**不阻塞状态流转**）。**未开启讨论的任务允许直接变更状态，但目标为执行（in_progress）/验收（accepted）时必须弹阻断式「未经讨论决策」风险确认**；进入待办（pending）、标记阻塞等低风险流转不拦，避免提示疲劳。

## 5. 设计稿呈现

[设计稿/squeeze-flow.html](设计稿/squeeze-flow.html) 覆盖全链路可点击：反馈进挤压区 → 详情依据摘要 → **沟通空间**（议题/观点/结论全过程）→ 结论回写 `task.decision` → 拆解 → 执行 → Agent 提问 → 执行上下文注入规则。详情与沟通空间的职责分离为本稿的结构基线。原型中的每个交互在 [设计稿/README.md](设计稿/README.md) 的**升级落点表**中标注对应的真实组件与端；原型本身是两端共用的语义示意，工程实现按落点分端进行。

## 8. 验收要点

1. 反馈「进入挤压区」后，Web 面板与桌面 Work 页均出现挤压段卡片，徽标「讨论中」，详情可见项目/仓库/反馈深链。
2. **职责分离与讨论门槛验收**：未开启讨论的详情无讨论状态区域、只有「开启讨论」（徽标「未讨论」）；开启后进入沟通空间，Agent 自动给出初步分析，参与者可添加用户；结论草案经多数决（Agent 不计入分母，单人提交即通过）显性通过后，详情「处理依据」常驻并标注回写 `task.decision`；Agent 过程摘要异步生成且不阻塞流转。
3. **风险门禁验收**：未开启讨论的任务直接执行弹「未经讨论决策」阻断确认，取消后状态不变，确认后落 `in_progress` 并写 `task.state_changed`；已开启讨论的任务执行不弹。
4. 非参与者/Agent 起草、投票、通过均被拒；通过后卡片离开挤压区，`project_events` 有 `discussion.approved`，反馈状态按既有链路回写。
5. **执行上下文验收**：`continuationContext` 读 `task.decision` 结论一行，不含讨论全文与过程摘要（对照 `buildAutomationTask` 现状断言）。
6. P2：决策后落 `pending` 可被 `buildPendingCandidates` 收入；Work 详情「立即交给 ArcOrbit」可单任务领取；`attention.question` 同时出现在条幅与卡片提问条，任一端回复后两者关闭并发出 `agent_question` 通知。
