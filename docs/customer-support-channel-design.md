# 客户-内部双向协作通道设计

## 一、产品定位

### 核心价值主张

**让客户反馈的问题能够被及时响应、高效处理、全程可追溯**

- 客户端：反馈有入口、有响应、有进度
- 内部端：反馈有收集、有分流、有闭环
- 全程：文档可追溯、状态可追踪

### 本期目标

建一条从"客户反馈"到"问题解决"的完整链路，让客户能反馈、能收到响应，内部能处理、能追踪。

### 本期边界

- ✅ 做：SDK → Agent客服 → 卡片 → 内部处理 → 确认 → 交付 → 响应客户
- ✅ 做：全链路文档贯穿
- ❌ 不做：标品反哺、跨客户分析、复杂报表

## 二、链路设计

### 2.1 全景流程

```
┌─────────────────────────────────────────────────────────────────┐
│                        客户侧                                    │
│  SDK打开 → 选择反馈类型                                           │
│       ↓                                                         │
│  ┌─ 问题反馈/使用疑问 → 对话式入口                                │
│  │   Agent追问 → 形成结构化结果 → 客户确认 → 提交                  │
│  │                                                               │
│  └─ 功能建议 → 快速表单（可选对话式）                              │
│      填写建议内容 → 提交                                          │
└─────────────────────────────────────────────────────────────────┘
                              ↓ 反馈进入系统
┌─────────────────────────────────────────────────────────────────┐
│                        Agent客服                                 │
│  知识库匹配 → 能解答 → 直接回复客户                                │
│       ↓ 无法解答                                                │
│  追问收集(明确场景/复现步骤/期望) → 信息完整 → 创建卡片              │
└─────────────────────────────────────────────────────────────────┘
                              ↓ 创建卡片
┌─────────────────────────────────────────────────────────────────┐
│                        内部处理                                  │
│  卡片进入项目空间 → 选择处理方式(Agent自动/人工介入)                  │
│       ↓ 处理完成                                                │
│  人工确认(可配置：文档/架构/代码) → 交付 → 响应客户                  │
└─────────────────────────────────────────────────────────────────┘
                              ↓ 全程记录
┌─────────────────────────────────────────────────────────────────┐
│                        全链路文档                                │
│  原始反馈 → Agent对话记录 → 卡片状态 → 处理过程 → 确认记录 → 交付物   │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 客户侧交互设计

#### 为什么选择对话式为主

| 维度 | 表单式 | 对话式 |
|------|--------|--------|
| 客户体验 | 填写门槛高 | 自然语言，门槛低 |
| 信息完整度 | 依赖客户自觉 | Agent追问，主动收集 |
| 分类准确性 | 客户可能选错 | Agent理解后自动分类 |
| 截图/附件 | 需要专门上传 | 对话中随手发 |
| 复杂问题 | 难以描述清楚 | 可以多轮澄清 |

#### 对话式入口流程

```
客户打开SDK
    ↓
Agent主动问候："您好，请问遇到了什么问题？"
    ↓
客户自然语言描述（文字/语音/截图）
    ↓
Agent追问（如需要）：
  - "请问是在哪个页面遇到的？"
  - "能描述一下具体操作步骤吗？"
  - "方便截图一下错误提示吗？"
    ↓
Agent形成结构化结果，展示给客户确认：
  "我帮您整理一下：
   - 问题类型：功能异常
   - 位置：登录页面
   - 现象：点击登录按钮无反应
   - 期望：正常登录
   确认提交吗？"
    ↓
客户确认 → 创建反馈记录
```

#### Agent回复方式

SDK提供消息推送能力：

| 方式 | 说明 | 推荐场景 |
|------|------|----------|
| WebSocket实时推送 | 客户端建立连接，实时推送 | 首选，体验最好 |
| 轮询 | 客户端定时拉取新消息 | 实现简单，有延迟 |
| Webhook回调 | 调用客户预留的通知渠道 | 异步场景 |

#### 保留表单入口的场景

- **功能建议**：诉求明确，可以直接填写
- **简单问题**：客户明确知道问题类型
- **批量反馈**：需要快速提交多个问题

### 2.3 核心状态机

```
客户打开SDK → 选择反馈类型
  ↓
┌─ 问题反馈/使用疑问 → 对话式
│   ↓
│   [对话中] → Agent追问 → 信息收集完成 → 客户确认 → [待响应]
│                    ↓ 信息不完整
│               [等待补充] → 客户补充 → [对话中]
│
└─ 功能建议 → 快速表单
    ↓
    [待响应]
  
[待响应] → Agent客服介入
  ↓
[处理中-知识库匹配] → 匹配成功 → [已响应-待确认] → 客户确认 → [已关闭]
  ↓ 匹配失败
[处理中-追问收集] → 信息完整 → [已创建卡片]
  
[已创建卡片] → 分配处理人
  ↓
[处理中-人工处理] / [处理中-Agent自动处理]
  ↓ 处理完成
[待确认] → 人工确认 → [已交付] → 响应客户 → [已关闭]
```

### 2.3 客户反馈类型

| 类型 | 说明 | 处理方式 |
|------|------|----------|
| issue | 功能异常、bug | 优先处理 |
| suggestion | 功能建议、优化 | 评估后排期 |
| question | 使用疑问 | Agent答疑 |
| consultation | 需求咨询 | 转销售/解决方案 |

## 三、落地路径

### 本期（4-6周）：跑通最小闭环

**目标**：一个客户能反馈，一个内部人员能处理，能响应结果

| 阶段 | 周期 | 交付物 | 说明 |
|------|------|--------|------|
| Phase 1 | W1-2 | SDK基础版 | 提交反馈、查看我的反馈 |
| Phase 2 | W2-3 | Agent客服MVP | 知识库匹配、基础追问 |
| Phase 3 | W3-4 | 卡片系统 | 创建、分配、状态流转 |
| Phase 4 | W4-5 | 人工确认 | 确认界面、状态回写 |
| Phase 5 | W5-6 | 全链路文档 | 反馈记录、处理过程存档 |

### 下期（6-8周）：完善体验

- Agent客服能力增强（多轮对话、意图识别）
- 批量处理、优先级管理
- 数据看板（响应时间、解决率）
- 标品反哺（共性需求识别）

### 远期：规模化

- API开放
- 高级分析
- 与其他系统集成（如Jira、飞书）

### 4.3 数据模型扩展

#### 反馈记录

```yaml
feedback:
  id: FB-001
  source: sdk
  customer_id: C-001
  type: issue | suggestion | question | consultation
  input_mode: dialog | form  # 对话式或表单式
  status: collecting | pending | processing | resolved | closed
  priority: high | medium | low
  title: "登录时遇到错误"  # 对话后形成
  description: "详细描述..."  # 对话后形成
  screenshots:
    - url: "https://..."
  # 对话式特有字段
  conversation_id: CONV-001
  collection_status: incomplete | complete  # 信息收集状态
  created_at: 2025-01-01
  updated_at: 2025-01-01
```

#### 对话记录

```yaml
conversation:
  id: CONV-001
  feedback_id: FB-001
  mode: dialog  # dialog 或 support
  turns:
    # 对话式收集阶段
    - role: agent
      action: greeting
      content: "您好，请问遇到了什么问题？"
      timestamp: 2025-01-01T10:00:00Z
    - role: customer
      content: "登录时遇到错误"
      attachments:
        - type: screenshot
          url: "https://..."
      timestamp: 2025-01-01T10:00:30Z
    - role: agent
      action: ask_clarification
      content: "请问您使用的是什么浏览器？"
      timestamp: 2025-01-01T10:00:33Z
    - role: customer
      content: "Chrome 120"
      timestamp: 2025-01-01T10:01:00Z
    # Agent形成结构化结果
    - role: agent
      action: present_summary
      content: |
        我帮您整理一下：
        - 问题类型：功能异常
        - 位置：登录页面
        - 现象：点击登录按钮无反应
        - 期望：正常登录
        确认提交吗？
      summary:
        type: issue
        location: "登录页面"
        symptom: "点击登录按钮无反应"
        expected: "正常登录"
      timestamp: 2025-01-01T10:01:30Z
    - role: customer
      action: confirm
      content: "确认"
      timestamp: 2025-01-01T10:02:00Z
  # 支持阶段（处理中客户追问）
  resolution: created_card
  resolved_at: 2025-01-01T10:02:00Z
```

#### 卡片

```yaml
card:
  id: CARD-001
  feedback_id: FB-001
  project_id: PROJ-001
  type: bug | feature | improvement
  priority: high | medium | low

  description: "..."
  assignee: USER-001

  created_at: 2025-01-01
  updated_at: 2025-01-01

    - type: document
      path: arckit/spec/authentication.md
    - type: code
      commit: abc123
```

#### 确认记录

```yaml

  id: CONF-001

  type: document | architecture | code
```

## 五、业务模式

### 5.1 角色定义

| 角色 | 职责 | 使用端 |
|------|------|--------|
| 客户 | 提交反馈、查看进度、确认结果 | SDK/小程序 |
| Agent客服 | 自动答疑、追问收集、创建卡片 | 后台自动 |
| 内部处理人 | 处理卡片、交付结果 | 内部平台 |
| 确认人 | 审核交付物、确认关闭 | 内部平台 |
| 管理员 | 配置规则、查看数据 | 管理后台 |

### 5.2 业务规则

#### 响应SLA

| 环节 | SLA | 说明 |
|------|-----|------|
| Agent响应 | <3秒 | 即时响应 |
| 人工响应 | 工作时间4小时内 | 首次响应 |
| 交付确认 | 处理完成后24小时内 | 客户确认 |

#### 卡片分配规则

- 自动分配：按项目、类型、优先级匹配处理人
- 手动分配：管理员指定
- 升级规则：超时未处理自动升级

#### 确认规则（可配置）

| 变更类型 | 是否必须确认 | 默认行为 |
|----------|--------------|----------|
| 文档变更 | 是 | 必须确认 |
| 架构变更 | 是 | 必须确认 |
| 代码变更 | 可选 | 按风险等级 |

### 5.3 计费模式

**按问题处理量 + 效率溢价**

| 计费项 | 逻辑 | 理由 |
|--------|------|------|
| Agent客服解决 | 按次计费，单价低 | 自动化处理，边际成本低 |
| 人工介入处理 | 按次计费，单价高 | 消耗人力，价值高 |
| 加急处理 | 额外加价 | 时间价值 |
| 全链路文档 | 包含在基础服务中 | 不单独收费，保证体验完整 |

**定价锚点**：对标客户现有"人工客服+工单系统"的成本，给出明确的降本比例。

## 六、协作模式

### 6.1 客户协作

```
客户打开SDK → 选择反馈类型
    ↓
┌─ 问题反馈/使用疑问 → 对话式
│   ↓
│   Agent即时响应，开始对话
│   ↓
│   Agent追问（收集必要信息）
│   ↓ 信息完整
│   形成结构化结果 → 客户确认 → 提交
│
└─ 功能建议 → 快速表单
    ↓
    填写建议内容 → 提交
    
    ↓
[待响应] → Agent客服介入
    ↓
    能解答 → 直接回复客户 → 客户确认 → 关闭
    ↓ 不能解答
    创建卡片，告知客户"已转内部处理"
    ↓ 处理完成
    推送结果，客户确认
    ↓
    关闭
```

### 6.2 内部协作

```
卡片进入队列
    ↓
自动分配/手动分配
    ↓
处理人认领
    ↓ 处理中
    ├── 需要调用Agent自动处理 → Agent执行
    ├── 需要人工介入 → 人工处理
    └── 需要协作 → @相关人员
    ↓ 处理完成
提交确认（按配置的确认类型）
    ↓
确认人审核
    ├── 通过 → 交付 → 响应客户
    └── 驳回 → 退回处理
```

### 6.3 信息流

#### 客户侧看到的

- 反馈状态：待响应 → 处理中 → 已交付 → 已关闭
- 处理进度：Agent回复 / 已转内部 / 处理中 / 待确认
- 最终结果：解决方案 / 修复版本 / 暂不处理说明

#### 内部看到的

- 卡片详情：客户信息、反馈原文、Agent对话记录
- 处理历史：谁处理了什么、什么时候
- 关联文档：涉及的需求、设计、代码

### 7.2 全链路文档

```
arckit/
├── intake/
│   └── customer-feedback/
│       └── FB-001/
│           ├── metadata.yml
│           ├── conversation.md
│           └── resolution.md
├── cases/
│   └── active/
│       └── CASE-001/
│           └── linked_feedback: FB-001
└── spec/
    └── (因反馈而更新的规格文档)
```

### 7.3 Agent客服的知识库

**不独立构建知识库产品，复用现有能力 + 外部服务**：

| 能力 | 方案 | 说明 |
|------|------|------|
| 事实查询 | 复用Arckit facts（arckit-spec等） | 已有产品规格、技术方案 |
| 向量检索 | 外部服务（腾讯云向量检索/Milvus/Qdrant） | 成熟方案，按需调用 |
| 对话记忆 | 外部服务（TencentDB或类似方案） | 存储层不自建 |
| FAQ维护 | 手动维护 + Agent辅助沉淀 | 本期简单实现 |

```
知识库 = Arckit facts + 外部向量服务 + FAQ文件
        （结构化事实）  （语义检索）     （常见问题）
```

## 八、关键决策点

| 问题 | 建议 | 待确认 |
|------|------|--------|
| Agent客服的自主权 | 能直接关闭简单问题（如FAQ匹配），复杂问题必须创建卡片 | ⬜ |
| 卡片的颗粒度 | 一个反馈一个卡片，可以关联多个反馈 | ⬜ |
| 确认人的角色 | 可配置，默认为项目Tech Lead | ⬜ |
| 响应客户的渠道 | 本期仅SDK内消息，下期支持邮件 | ⬜ |
| 知识库来源 | 从arckit/spec/自动同步 + 手动维护FAQ | ⬜ |
| 卡片与Case的关系 | 卡片是Case的一种来源类型 | ⬜ |

## 九、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| Agent客服回答不准确 | 客户体验差 | 设置置信度阈值，低于阈值转人工 |
| 卡片积压 | 响应超时 | 设置预警机制，自动升级 |
| 确认流程过长 | 交付延迟 | 可配置确认类型，低风险跳过 |
| 知识库过时 | 答案错误 | 定期同步spec，标记过期内容 |
